# 2026-09-21 17:0x · A 项：停在待人工处的会话不再被收尾抹成「已完成」

来源：治理计划收官时登记的余账第 1 条（`plan/governance-handoff.md` §3，B2 那轮实测到、
按范围没修）。用户 17:00 前后的指令是「现在开始修」，本项是第 1 个。

## 段 1 · 现象

会话停在 interrupt（审批卡/追问）之后，`store.status` 显示 `finished`：

- 图上并没有跑完——`astream_events` 因 interrupt **正常结束**，不是异常；
- `_translate` 在 `on_interrupt` 分支明明置了 `awaiting_human`（`server/runner.py:434`）；
- 界面上看不出来，是因为前端在收到 `approval`/`ask_human` 事件时自己本地补了一刀
  （`frontend/src/stores/sessions.ts:414`、`:423` `mergeSessionLocal(..., {status:'awaiting_human'})`）
  ——**刷新一次或走 GET 就露馅**：侧栏点变灰、状态标签变「已完成」，而待批卡还挂在审批队列里。

连带失效的前提有三处，全建在 `store.status` 上：

| 位置 | 写的前提 | 状态被抹掉之后的实际后果 |
|---|---|---|
| `server/api/sessions.py:214` `start_session` | 「running/awaiting_human 必有人在跑」→ 409 | 放行重开，同一 `thread_id` 再灌一场，把 checkpointer 里等人回答的那个断点冲掉 |
| `server/runner.py:73` `stop()` | 同上一条 → 转发 `ch:ctl` | 只要状态侥幸停在 awaiting_human，转发给没有任何任务的 worker → 会话钉死在 `stopping` |
| `platforms/session_store.py:124` `heal_running()` | 重启自愈把 running/awaiting_human 改 `stopped` | 这条永远命中不到（早被抹成 finished），账面「等人回答」的会话重启后无人收 |

## 段 2 · 排查过程（实际命令与输出）

1. 先证实状态确实被覆写，而不是 `_translate` 没置位——用治理计划留下的现成载体
   `tests/s17_human_input_guard.py::t1`（假图产一个 `on_interrupt` 事件、真 `SessionRunner._run`）。
   它当年就是为这条读数写的，但**只 print 不 assert**（原话「把收尾时的 store 状态如实记进读数
   （不假设）」）。跑：
   ```
   PYTHONPATH=/e/Codeharness:/e/Codeharness/logs PYTHONIOENCODING=utf-8 PYTHONDONTWRITEBYTECODE=1 \
     F:/anaconda/python.exe -B tests/s17_human_input_guard.py
   ```
   修复前读数：`store 状态='SessionStatus.awaiting_human'`?? —— 我第一次把断言写成
   `str(store.get(sid).status) == "awaiting_human"` 时**当场红**，红字打出
   `'SessionStatus.awaiting_human'`：`str(枚举)` 在本机 Python 3.13 上是类限定名，
   只有 `.value` 才是 `"awaiting_human"`（`_publish_status` 早就用 `.value` 不是没道理）。
   改成 `.value` 后同一格打出 `'finished'` —— 覆写成立，根因位置没跑。
2. 定位覆写点：`grep -n "SessionStatus.finished" server/runner.py` → 两处
   （`_run` 收尾、`_resume` 收尾），行号与治理计划登记的 `:356`/`:231` **一字不差**（我今天
   复核过，说明这条线期间没人动过这两句）。
3. 判「该谁改」：`awaiting_human` 是不是有合法消费者？查下来三条支持保留它——
   ① 前端词汇表把它算进 `isActive`（`stores/sessions.ts:80`）并有专门样式
   （`SessionRow.vue:123` 「等待回答」、`:135` 还配了 `hasPendingApproval`）；
   ② `UsagePage.vue:47` 有中文标签「待人工」；③ `_forget` 的 docstring 自己写着
   「awaiting_human 时必须留着供 resume」——可是收尾走的是 `terminal=True`，把它自己的口径违反了。
   即：**前端与内核都按「这是驻留态」设计，只有 runner 收尾那两句按「瞬时态」写**。
4. `stop()` 半边单独取证：`SessionRunner._ctl` 为 None 时不转发，但 redis 模式一定非 None；
   跨 worker 情形下 `answer_human`→`_resume` 一起手就把状态改成 running（`:226`），
   所以「awaiting_human 且有活任务」这个组合**不存在** → 转发的对端必然是空手，
   落 stopping 就是死状态。这条推理随后被 t4① 的读数钉住（就地落 `stopped`、`stop()` 回 True）。

## 段 3 · 根因

两条 teardown 各写一遍「无条件 finished + run completed + 散会」，没有看这一场是不是停在断点上。
是**重复代码导致的语义漏检**，不是判断写错——所以修法是把两处收进一个共用出口，在出口里判状态。

## 段 4 · 解决方案

1. `server/runner.py` 新增 `_settle(sid)`（放在 `_fail` 前面，与 `_forget`/`_publish_status` 同层）：
   状态仍是 `awaiting_human` 时**只发状态事件不散会**（`_forget(terminal=False)`，graph 留给
   resume，照 `_forget` docstring 的原有口径）；否则照旧写 `finished` + `finished_at` + 散会。
   `_run`、`_resume` 两处三行 teardown 全换成 `self._settle(sid)`。
2. `stop()`：把 awaiting_human 从「转发 `ch:ctl`」那一支里摘出来，就地
   `store.update(stopped, finished_at)` + 发状态 + `_forget(terminal=True)` + 回 True。
   转发包围条件收紧成 `status == running`。
3. `server/api/sessions.py:start_session`：两个 409 分开。running → 原文案
   `session already running`；awaiting_human → `会话停在待人工处：请先回答，或点停止放弃这场`
   （状态码不变，前端 toast 直接吃 detail，零前端改动）。
4. 契约回写：`docs/前端/接口契约.md` 状态词汇表下面加一段「awaiting_human 是驻留态」，
   把两条去路与 `/start` 的 409 写清，并点名前端那处本地补态（它从此是冗余而不是遮丑）。
5. 门禁转正：`tests/s17_human_input_guard.py` 从 3 组扩到 **4 组**。t1 那句「不假设」的
   print 升级成断言；新增 t4 四格（①驻留 + graph 保留 + `stop()` 落 stopped；②正常收口照旧
   finished 且散会；③**对照组=修复前原样**：monkeypatch `_settle` 回那三行，同一载体必须读出
   `finished`，否则 ① 没有区分力；④端点级 `/start` 409 且 detail 含「待人工」）。

**未验边界**（照 §0.5 写清，不许拿假图读数冒充）：

- 断言打在**假图产 `on_interrupt` 事件**这条构造路径上，不是真 langgraph interrupt 的端到端。
  真图那一侧由 `s3b` t7/t8（真落断点）覆盖，但它不读 `store.status`。
- 多 worker 下的 `stop()` 转发收紧（awaiting_human 不再上 `ch:ctl`）**只有单进程读数**；
  redis 双进程形态没起。判据依据是段 2 第 4 步那条推理（resume 一起手就是 running）。
- 活体界面（刷新后侧栏点是否真变「等待回答」）**没取读数** —— 需要 8721 隔离实例 + 一条真停在
  审批上的会话。前端本地补态那条通路本来就把它显示对了，所以这条不是判据缺口而是留证缺口。
- 一处行为变化要留意：停在断点的会话现在会把 `graphs`/project 的常驻 shell 留到回答或停止为止
  （旧写法每次都收）。这是 `_forget` docstring 声明的意图，代价是「等人回答然后人去睡」的会话
  多占一个 `cmd.exe` 直到进程重启；`heal_running()` 会在重启时把它落成 `stopped`。

**过程中我自己踩到的**：`str(SessionStatus.x)` 在本机不是 `"awaiting_human"`（段 2 第 1 步）。
这条已写进上面读数，别在别的判据里再撞一次——要字符串用 `.value`。
