## 3 · 根因

**不是测试独有问题，是生产路径的静默丢事件窗口。**`/events`（`server/api/sessions.py:266-277`）的走法是：

```
q = bus.subscribe(sid)          # 只建任务，游标还没定
for ev in bus.history(sid, after):   yield ...   # 同步取历史
while True: await q.get() ...               # 之后靠 reader 续推
```

落在「`history()` 已取完」与「reader 首次 `xrevrange` 定尾」之间的 XADD：
- 不在已回放过的事件里（`history()` 在它之前就读完了）；
- 又被算进 reader 眼中的「流尾」→ `xread({key: start})` 只回 `start` **之后**的条目，**永远读不到它**。

→ 该事件对这条 SSE 连接**永久丢失**。测试之所以偶发，是这条窗口只有微秒级：单跑 t12 时任务调度赶在前面就过，
套件里负载/顺序变了就输。进程内那台 bus 没有这个洞（`subscribe` 同步登记队列，登记后的 publish 必然进队列）。

## 4 · 解决方案

**改根因，不改症状**（两处，一个 commit `71bb22d`）：

1. `platforms/event_store.py::RedisEventBus.subscribe`：**返回前**用同一个同步客户端把流尾钉死
   （`self._sync.xrevrange(key, count=1)`），reader 改成 `nonlocal start` 只做 `xread`。
   语义从「可能漏」变成**至少一次**——重复的那几条正好由调用方已回放的 `history()` 覆盖，
   前端按定宽 `cursor` 去重（SSE seq 精度丢事件那次修复已把去重键从 seq 换成 cursor）。
   同步调用不是新引入的阻塞：这个类的 `history()` 本来就走 `self._sync`，注释里已写明「每连接一次、亚毫秒」。
2. `tests/s7_platform.py::t12`：内层 3s 超时单独 `raise AssertionError("subscribe 后 3s 内没收到续推事件——流尾游标竞态？")`
   并 `from None` 掐掉链，不再冒成外层「60s 卡死」。
