# 2026-09-21 21:0x · C1 地基片：未知收件人不再静默丢（委派抛、插话丢+留痕）

用户 18:3x 拍 C1「做完整多角色委派、允许现场新建角色」，19:5x 又定了我追问的四条档位
（profile 现场写 / 声明式工具走同一条审批门 / 新角色持久到 `session.roles` /
**未知收件人当场抛错**）。顺序是先落这条**先决地基**，再上委派载体与 planner——
因为现在的静默丢弃会让后面任何一条装配错误都变成"跑完了但什么都没产出"。

## 段 1 · 现象

三类"收件人不存在"全都静默：

| 位置 | 旧行为 | 后果 |
|---|---|---|
| `route()` 的 SOP 订阅表目标 | 直接 `Send` 给不存在的节点名，LangGraph 只打一行 `Ignoring unknown node name PM` | **整场零次 LLM 调用**，会话"正常结束"且零产物（`_default_agents` 的注释与 docs/对照5:95 都记过） |
| `route()` 的具名 `send_to` | `if name in agents` 不命中就当没这条 | 委派悄悄蒸发，`Command.assignee` 写错人没人知道 |
| `route()` 的 `<self>` 回喂 | 落到后面的 targets 逻辑，最终 `END` | B9 的自愈回喂直接散会 |
| 插话（`CHAT_SINK`）| `if recv in agents` 不命中即丢 | 用户追问凭空消失 |

## 段 2 · 排查过程

1. 读装配面时发现：**委派今天的载体根本不存在**。`Command.assignee` 只在
   `roles/role_zero.py:174` 被拼进计划展示文本，全仓 `grep -rn assignee` 没有任何一处把它
   当路由输入；`codeharness/team.py:67` 的注释自陈「`Command.assignee` 只是展示字段，无委派路由」。
   所以"让 assignee 成 Send 目标"要先造载体（下一片），不是改两行路由表。
2. 改完 `route()` 跑全量门禁，两条红：
   - `s3b::t4_self_to_unknown_node` 钉的正是**旧的静默行为**（`if got == END: return`）→
     按新契约改判成"必须抛且点名 Ghost"，不是回退代码；
   - `s7::t13_dual_runner_fakellm_line` 变成 `failed`。我没有猜原因，直接去找投递形状：
     该用例故意 `factory(s.id).enqueue("另一worker的插话", "Ghost")` 证明跨 worker 消费。
     我把 C1-d 一刀切到插话路径后，**一根错名字把整场会话打成了 failed**。
3. 这两类代价不对称，摆到用户面前定了档（选项：委派抛+插话丢告警 / 一律抛 / 插话退回队长），
   用户选**委派抛、插话丢 + 留痕**。

## 段 3 · 根因

`route()` 把"目标存不存在"当成过滤器而不是契约：`if name in agents` 只用来避免
"给 LangGraph 发一个未知节点导致它抛 Unknown node"，顺手把"指名指错"也一起吞了。
防 Send 到未知节点是对的，但吞掉错误信息是另一件事。

## 段 4 · 解决方案

1. `team_graph.py` 新增 `UnknownRecipient(ValueError)`；`route()` 三处改判：
   `<self>` 的 `sent_from` 不在册 → 抛；SOP 表目标不在册 → 抛；具名 `send_to` 不在册 → 抛。
   错误文本一律带**那个名字 + 在册名单**，不然又是一条要人反查的日志。
   `<all>/<none>/<self>` 三个标记不参与"存在性"判定（把它们当角色名会把所有默认值消息全炸）。
2. 插话路径按新档位：丢弃 + `logger.warning` + `stats` 里记一条 `chat-dropped`，**不抛**。
3. 顺带修 `build_team` 的 `sop or SOP`：显式传空表会被 falsy 吞成默认表。
   我写隔离用例时正好撞上（拿不到"只靠具名投递"的形状）。改成 `SOP if sop is None else sop`。
4. 门禁：
   - `s16::t6_unknown_recipient_raises` 五格（①具名 ②SOP 表 ③`<self>` 三格必抛；
     ④**阳性对照**：合法具名投递照常送达，证明不是一律抛；⑤`<all>` 既不抛也不广播）；
   - `s3b::t3b_chat_to_unknown_role_is_dropped` 钉插话档：Ghost 丢、QA 送达、
     `stats` 里有 `chat-dropped`（没留痕=静默丢，同样判红）、队列被消费干净；
   - `s3b::t4` 按新契约改判。

## 段 5 · 解决后效果（读数）

`s3b_runtime` **17 组 exit 0**（原 16 + t3b）、`s16_route_state` **6 组 exit 0**、
`s7_platform` 13/13 全绿、`s21` 3/3、`s8` 14/14；`s1/s2/s3/s4/s5/s6/s12/s14/s15/s20` 与
`build` 在同一次 sweep 里全绿（`log/c1_*.out`、`log/c1_final_*.out`）。

**照实记一条我自己没做到的**：我给用户的选项里写的是「往事件流发一条 error（前端红点行已能吃）」，
实现出来是 **loguru WARNING + `stats` 记账**，没进事件流。原因是 route 手上没有 bus——
要把 error 事件送到那里，得给 `make_route` 注入一条 bus（第四个 ContextVar）或给 ChatQueue
加一个 drop 回调，为一条"端点已经 422 挡过"的兜底路径付这笔不划算。
**这笔债记在这里，不当已满足**：如果用户要界面真看得见这条丢弃，接缝该做在
`ChatQueue`（投递时就知道目标不存在，比 route 更早）而不是 route 里。
