# 2026-09-21 18:0x · F 项：compose 容器形态的凭据读数（redis 半边补齐）

治理计划收官时 S5 留的**唯一无读数项**：`docker compose up` 全栈形态（镜像 entrypoint、
服务名解析、凭据真的生效）。当时挂起的理由是引擎未运行。今天 18:00 前后用户授权范围=
**只验 redis 容器**（不拉新镜像、不碰本机 6379 那个共享 Redis、不起 backend/frontend 镜像构建），
Docker Desktop 由我拉起（用户一句「帮我启动」）。

## 段 1 · 现象 / 待验的到底是什么

S5 的改动全在**声明层**：`docker-compose.yml` 里 `${REDIS_PASSWORD:?…}` 与
`QDRANT__SERVICE__API_KEY: ${QDRANT__API_KEY:?…}`，加上消费侧 `RedisConfig.to_url()` 带凭据、
`AsyncQdrantClient(api_key=…)`。收官那轮已经把**消费侧**用真服务+真进程读到
（`tests/s13_redis_qdrant_auth.py` t1–t6，qdrant 侧用官方 Windows 二进制同版本代替容器），
剩下的问题只有一个且很具体：**在 compose/镜像这个交付形态里，那两行声明是否真的落到容器 argv
并真的挡住匿名客户端**——`docker compose config` 只证明插值算对了，不证明 redis 收下了密码。

## 段 2 · 排查过程（实际命令）

1. 引擎：`docker info` 连不上 → 用户授权后 `cmd //c start "E:\Docker\Docker Desktop.exe"`，
   `com.docker.backend.exe` 起来后 ~10s `docker info` 通（`27.5.1 / Docker Desktop / 16cpu`）。
2. 端口：`docker-compose.yml` 钉的是 `6379:6379`，而 6379 已被 `redis-server.exe`
   （PID 11952，F:\Redis 的 Windows 服务，本机 dev 后端在用）占着 → as-shipped `up` 必然撞。
   按用户选的范围，用**临时 override 只改宿主端口**（`16379:6379`）绕开，不动仓库里那份 compose。
3. 起：`REDIS_PASSWORD=… QDRANT__API_KEY=… docker compose -p fixe5 -f docker-compose.yml
   -f <tmp override> up -d redis`（独立 project 名 `fixe5`，卷/网络都带前缀，不与任何在跑的
   东西共用）。缺密钥那半边今天早先已单独测过：同一份文件不带 `QDRANT__API_KEY` 时
   `config` **解析期** exit 15（`log/fixF_config_missing.out`）。

## 段 3 · 读数（`log/fixF_redis.out`）

| 判据 | 实测 |
|---|---|
| 密码进了容器 argv | `docker inspect fixe5-redis-1 --format '{{json .Args}}'` → `["redis-server","--save","60","1","--appendonly","no","--requirepass","prob3A1x"]` |
| 匿名客户端被拒 | `redis-cli -p 16379 ping` → **`NOAUTH Authentication required.`** |
| 带密码可用 | 同上带 `-a` → `PONG` |
| 读写真通 | `set fixe5:probe ok` → `OK`；`get` → `ok` |
| 共享实例没被牵连 | `netstat` 上 `127.0.0.1:6379` 仍是 PID 11952，`redis-cli -p 6379 ping` → `PONG`（本机 dev Redis 全程没停、没改） |

**收摊核对**：`down -v` 掉 `fixe5_redis_data`/`fixe5_workspace` 两个卷与 `fixe5_default` 网络；
临时 override 文件删掉；16379 **零 LISTENING**（只剩四条 TIME_WAIT 是我自己探针的连接残余）；
`docker ps -a`/`volume ls` 里 `fixe5` 计数为 0。Docker Desktop 保持运行（用户要求起的）。

## 段 4 · 结论：哪些算闭、哪些仍欠

- ✅ **redis 半边闭了**：compose 形态下声明→argv→服务端拒绝匿名→带凭据可用，四步全是真读数。
  这条与收官那轮的 `to_url()` 消费侧读数拼起来，S5 的 redis 侧不再有缺口。
- ⬜ **qdrant 半边仍欠"容器这一种载体"**：`qdrant/qdrant:v1.19.0` 本地没有（只有 `:latest`），
  在用户选的范围里拉镜像被排除了。要补的话两条路：拉 v1.19.0 tag，或者按 `s13` t5 已有的做法
  （官方 Windows 二进制同版本 `1.19.0`，服务端自报 commit 74f3e85b）——**语义侧其实已经验过**
  （无 key 401 / 错 key 401 / `api-key` 头 200 / 真建集合成功），欠的只是"compose 里那台容器起得来"。
- ⬜ **backend/frontend 镜像构建未验**：`build: .`（上下文=仓库根）+ `env_file: .env`，
  属另一个量级的动作（几分钟构建、可能改 `.env` 语义），本轮范围不含。

## 段 5 · 不是代码问题 / 我自己记一笔

本轮**零代码改动**，纯取证。两处容易误判的形状：
① `docker info` 早先 16:5x 取到过 "27.5.1 在跑"，17:5x 又不在了——Docker Desktop 会被自己或别的
会话关掉，**"引擎可用"这种读数只在取的那一刻成立**，动手前必须现取（我在 PLAN 的 F-F 行里为这句
话撤回报过一次）；② `grep -c ":16379"` 会数到 TIME_WAIT，端口是否真关要 `grep LISTENING`。
