# ADR-20260922-06 · 超时报错与重试语义

## 状态
已接受（2026-09-22 16:4x 用户拍板：**不应该自动重发**）—— 但落点与本仓实测细化成两半，见「决策」；实现时的两条纠正见文末「补记」（其中一条是本文件原来那句落点按字面做不生效）

## 背景
两件事被混在「C16 超时口径」这一条里。

① 缺陷（已修，主仓 `6c11209`）：`frontend/src/api/client.ts` 的 fetch 用本次传入的 `timeoutMs`，
   而超时那条文案硬取常量 `REQUEST_TIMEOUT_MS/1000`；上传走 `KB_UPLOAD_TIMEOUT_MS=120000`，
   于是等满两分钟界面会说「超时（15s 无响应）」——假数字比不报更带错方向。

② 提案「捕获 `asyncio.TimeoutError` 返回 504」有三处与本仓现实打架（都取过证）：
   - **落点不存在**：没有 `codeharness/api/endpoints.py`；端点在 `server/api/workspace.py`。而
     `_acall` 是网关的重试助手不是端点，upload_kb 这条路上**服务端根本没有请求级 deadline**
     （120s 那档只存在于前端 `AbortSignal.timeout`），要做 504 得先新增服务端超时，不是 catch 一下就有。
   - **异常形状接不到**：qdrant 客户端把连接失败裹成 `ResponseHandlingException`、embedding 端点裹成
     `APIConnectionError`，顶层类名都不提「连接」⇒ 照 `except ConnectionError` 写，
     会把 C16 已验通过的 `_unreachable()` 顺链判法改坏（该判据有反向验证：只看顶层类型即红）。
   - **`detail` 传 dict 会显示成 `[object Object]`**：`client.ts` 的 `flattenDetail` 只处理字符串与数组，
     其余走 `String(detail)`。所以「哪台 / 原件在不在 / 该查什么」必须是**文本**（现在的三行字符串就是为此）。

## 决策
1. **超时不自动重发**：`gateway.py:_retryable` 把 `asyncio.TimeoutError` 从可重试集合里挪出去。
   理由与用户一致——幂等无法保证（KB 上传原件已先落盘）、成本不透明（¥0.27/句，重发即翻倍）、
   掩盖问题（用户应知道「服务在但没及时回话」）。
2. **但连接类失败保留重发**：`ConnectionError/OSError` 与「非 status 的 `APIError`」仍然重试。
   仓内实测依据写在 `_retryable` 注释里：qwen MaaS 的 `Model output became abnormal while generating a
   JSON response` 属**瞬态、同一请求重发即成**；连接建立失败意味着**没受理**，重发不产生第二笔钱。
   ⇒ 口径是「**可能已受理的不重发**」，不是「超时和连接失败都不重发」。
3. **504 暂缓**，先补 C18 的账：待批会话被 `heal_running()` 抹成 stopped、批准后连接失败直接判 failed。
   真要端点级 deadline + 504 时，`detail` 继续用字符串（可加一行「重传是安全的：切片 id 由内容派生，
   同内容重传不堆积」——这是 C3 已有的幂等事实，比 `file_may_exist` 的"可能"更准），
   错误码说明只写 `docs/前端/接口契约.md`，不新建 `docs/api/errors.md`。
4. 用户提的 `retry_allowed` / 前端 `showWarning` 分支：语义采纳，形态不采纳——本仓 `req()` 已把
   非 2xx 的 `detail` 原样翻成 `Error.message`、`DetailsPanel` 按 `err.status` 分流（F-E/C16 两侧同判），
   再加一套并行渲染规则就是第二本账。`fetch(..., {timeout})` 不是真 API（本仓用 `AbortSignal.timeout`）。

## 后果
正面：钱与副作用不会因为一次超时翻倍；日志里「用户主动重试」与「系统自动重试」不再混在一起；
瞬态连接错误仍会自愈（不牺牲 C3/C5 那两条实测换来的鲁棒性）。
负面/已知边界：真挂死的端点会让用户等满一个 timeout 才看到话（无自动重试兜底），这是知情权的代价。
504 与端点级 deadline 仍未做，登记在 `plan/PLAN.md` §4 C18 行。

## 补记（2026-09-22 17:5x，C18② 落地时取到的两条纠正）

1. **「决策 1」那句落点按字面做不生效**。写的是「`_retryable` 把 `asyncio.TimeoutError` 从可重试集合里
   挪出去」，但 Python 3.11 起 `asyncio.TimeoutError` **就是**内置 `TimeoutError`，而 `TimeoutError` 是
   `OSError` 的子类（本机 3.13 实测：`issubclass(TimeoutError, OSError) is True`）——从元组里摘掉名字，
   下面那支 `isinstance(exc, (ConnectionError, OSError))` 照样放行。另一半同理：`openai.APITimeoutError`
   是 `APIConnectionError` 的子类、后者是 `APIError` 的子类（**不是** OSError），所以「非 status 的 APIError
   仍重试」那支也会把超时放回来。⇒ 真落点是**在 OSError 之前先挡一道**：
   `if isinstance(exc, (TimeoutError, asyncio.TimeoutError, APITimeoutError)): return False`。
   判据 `tests/s2_gateway.py::t14`（看**桩收几次**：超时 1 次、连接失败 3 次；只看返回值的话
   「不重发」与「重发后成功」长得一样）；反向验证两轮各红在这两句上（一轮换回旧写法、一轮只挡
   `APITimeoutError` 漏掉内置 `TimeoutError`，后者专钉这个陷阱）。
2. **C18② 的证据句里「没有重试」那半不准**：批准后那一发走 `structured()`/`aask` → `_acall`，
   连接类失败按本决策**本来就重发**（实测 3 次）；真正缺的是重发用尽之后的那声响，所以②的实现
   落在 `server/runner.py::_fail` 的告警（`[session-failed]`）与事件可见性上，不在重试次数上。

## 补记（2026-09-24 15:4x，C25 落地时取到的三条）

1. **429 是本决策没覆盖的第三档，今天起可重**。当时只拍了「超时不重发 / 连接类仍重发」两半，而厂商限流
   正好落在两不管的空档：`RateLimitError` 是 `APIStatusError` 的子类，按旧判据不重发 ⇒ 多角色会话跑到一半
   整场作废、前面烧掉的产出全废。09-24 在 StepFun `step-3.5-flash` 上量到它限的是**在途请求数**
   （`current: 6, limit: 5`）：in-flight 1/3/5 各发各的零撞、6 起 1/6 撞、8 起 3/8 撞；**带退避重发之后
   6/6 与 8/8 全过**（同形状总墙钟 0.48s → 1.63s，重发用了 1 与 3 次）。被拒那一发**没受理、不产生第二笔钱**
   ⇒ 它不是「超时（再发可能更糟）」，是「等一等就好」。落点 `_retryable`：
   `if isinstance(exc, APIStatusError): return exc.status_code == 429`——**只认 429**，其余状态码照旧 False。
2. **「有界 3 次」在真 SDK 上其实是 9 个请求，而且一声不出**。`ChatOpenAI` 不传 `max_retries` 就用 openai
   SDK 的默认 2（langchain 那个字段默认是 `None`＝交给 SDK）⇒ 两层各 3 次；本地 429 桩现证**桩收 9 次 /
   7.29s**。更要紧的是 SDK 那层重发的正是**超时与连接错**——本决策第 1 条「超时不自动重发」在 SDK 面前
   一直是空话，只是平时被外层同值的 `wait_for` deadline 遮住看不见。⇒ 今天钉 `max_retries=0`
   （`gateway.py:73`），**重试的归属只有一处**：`_acall`。判据在 `tests/s2_gateway.py::t17④`，
   那里客户端 timeout=1s、外层 deadline=20s 故意不同值——两者同值时外层先取消，那一格就成了恒真。
3. **重发要出声**。补记 2 第 2 条说过「缺的不是重试次数，是那声响」，今天补两处：`_acall` **每次退避**记一行
   warning（429 的形状是「会话照旧成功、只是慢」，`runner._fail` 那条终态告警看不见它），而 t17 钉的是
   **喊了几声**（撞两次成功＝2 声，不多不少）——静默兜住与刷屏都算坏。
