# ADR-20260923-08 · embedding 输入长度上限（H 是端点属性，不是常量）

## 状态
提议（2026-09-23 落笔，`date` 现取）。三个子决策（H 走配置且默认 1200 中文字 / 记忆腿也切 /
`.docx`+`.pdf` 由统一出口顺带覆盖）已由用户在 `plan/PLAN.md` §4 C27 行定死；本文件只把**口径**与
**实测依据**登记成第二份可查的地方，**会话不自批**——批了才转「已接受」。

## 背景
OpenAI 兼容的 embedding 端点对超长输入**静默截断**：不报错、不返回任何标记。本机 bge-m3 两个读数：

| 量法 | 读数 | 出处 |
|---|---|---|
| 重复串前缀 + 尾部特征句 | 前缀 3600 字起尾句信号恰为 `+0.0000`，两串向量**逐维相同**（3192 字仍有 `+0.181`；特征句放句首则 4800 字仍 `+0.326` ⇒ 保头丢尾） | 仓库外探针 `E:/tmp/ch_trunc2.py` / `E:/tmp/ch_trunc2.out`（09-23 立账时取） |
| **真文档复量**（PLAN 当时明写「3600 是观测上限不是安全值，落地前用真文档重量」） | 仓里 `docs/*.md` 拼出的 39,325 字中文散文：**全文向量与 `doc[:3200]` 逐维完全相同** | `tests/manual_embed_truncation.py` 的 A 格（09-23 实跑） |

真文档比重复串**更早**触顶（3200 < 3600），所以取更保守的那条当依据。

四条入库路当时的形状（这就是「等于没切块」的三条）：`.txt/.md` 那个 splitter（`document.py:47`
`chunk_size=256`）**只在有换行处生效**——实测 900 字不换行的段落原样出一块，langchain 自己打警告
`Created a chunk of size 400, which is longer than the specified 256`；`.pdf` 按页、不看长度；
`.docx` 整篇一块；默认开着的记忆腿最坏（`longterm.overflow` 把整条消息当一个点，而 `read_file`
单次可回 2 万字符）。

**这个洞为什么一直没被归因**：词法腿（`qdrant_store.sparse_from_text`）是本地 Python 从**全文**算的、
不经端点，所以症状是「按原文关键词问得到、换个说法问不到」——看着像模型笨，不像索引缺。
推论（已写进判据）：**量尾部可达必须 `hybrid=False`**，否则词法腿把整条大点顶进 top-k，测的是词法不是向量。

## 决策
1. **唯一出口** `codeharness/document_store/embed_split.py::split_for_embedding(texts)`：任何要进向量
   端的文本先过它。优先在换行处断，单行本身超上限才硬切；短于上限的原样通过（⇒ 今天绝大多数
   入库的**点 id 与改前逐字节相同**）。
2. **H 进配置**：`EMBEDDING__MAX_CHARS`，默认 **1200**（真文档窗口 3200 的一半以下，留 token
   密度余量）。上界由 validator 钉在 `EMBEDDING_OBSERVED_TRUNCATION_CHARS = 3200`：非正、或大到超过
   观测窗口，**在 settings 构造期抛**（照 C5 那条纪律：坏配置不许「能跑但保护没了」）。
   **这条上界原本写的是 3600**——立账那条读数是重复串前缀量出来的，台账当时就自陈「3600 是观测上限
   不是安全值，落地前用真文档重量」；A 格拿真文档重量完更早触顶（3200），于是**按实测把常量与三处
   引文一起改准**，不是照抄立账值。C 格实测过这条上界不是装饰：一块 3600 字的文本与它的前 3200 字
   **向量逐维相同**。
3. **记忆腿也切**（用户定）：一条长消息 → N 个切片点，各带自己的原文与那条消息的元数据。
4. **`.docx`/`.pdf` 由统一出口顺带覆盖**（用户定）：C26 那只管「白名单不许撒谎」，粒度归这里。
5. **本项不做**：overlap、块大小调优、语义切/结构化切/父子块。那些是调优，等 C20 那把有判别力的
   检索基线尺子（口径已定死，别顺手扩）。
6. **经验腿不碎成 N 点**（会话的决定，写明代价与重开条件）：`exp_point_id` 同时就是 Redis 命中计数
   的键，一条经验 = 一个点。签名超上限时取首块 + `logger.warning`。
   **代价**：签名超过 1200 字的部分进不了向量（payload 文本仍是全文，召回回来的内容不缺）。
   **重开条件**：`EXP_POOL__ENABLED` 真打开（今天默认关、`enable_read/enable_write` 也默认关）且现场
   量到长签名——那时改成 N 个点、payload 带 `exp_id` 做读侧去重。

## 后果
正面：尾巴不再静默消失——同一份 2 万字文档、同样 12 条干扰项、dense-only 用「只有尾部才有的那句
事实」提问：走出口碎成 31 块 → **命中 top-1**（cos 0.542）；按改前写法整条一个点 → **top-5 不命中**
（最佳 cos 0.374）。B 格那对正负读数是这个决策的全部价值。

负面/已知边界：
- **块内容变 ⇒ 点 id 变**（id 由内容派生）：改造前那些「整条大块老点」与新碎点**并存**，同一段话可能
  召出两次。dev 数据不迁移清洗（照 C4/C12 先例），要清按 `doc_type` + `user_id` 一次 `delete_scope`。
- **端点调用次数上升**：2 万字一条消息从 1 发变 17 发（`H=1200`）。本机 bge-m3 零现金；
  云端按量计费的 embedding 端点要按这条重算（同一份 12,000 字真文档的实测曲线
  `H=400 → 39 块`、`H=1200 → 12 块`、`H=2400 → 6 块`、`H=3200 → 4 块`；C 格另量到同一段 400 字文本
  连发四次**逐维相同** ⇒ 这台端点幂等，块内容与点 id 因此稳定可比）。
- **读侧未管**：`recall(query)` / `exp_store.search(query)` 把查询串整头发给端点——超过窗口的查询
  同样只看前 ~3200 字。本项判据只覆盖入库路（口径已写进 PLAN C27 行），查询侧超长今天没有现场需求。
  另一处 `aembed_documents` 在场但**不归本档**：`tools/tool_recall.py:157` 发的是工具名册文档串
  （实测全名册 18 只、`"名字: description"` 最长 210 字），离窗口差一个量级，不是长文本入库路。
- **〔09-24 后续；本档状态仍=提议，不自批〕读侧已管**：C32 先截 `LongTermMemory.recall`，C35 收成 `document_store/embed_split.clamp_query` **一处**、`recall` 与 `ExpStore.search` 两条召回腿共用（后者收的是用户原话，正是本条当时说「没有现场需求」的那类输入）；判据 `s5 t38` 打在**实发长度**上，四个变异各红在预期的断言上。上面那句「今天没有现场需求」按此改读，其余原文一字未动。
  ⇒ 全仓 `aembed_*` 共四处（记忆/知识库/经验池/工具召回），本项动了前三处，第四处按读数免动。
- 上限是**这台端点**的属性：换厂商/换模型要重跑 `tests/manual_embed_truncation.py` 的 A 格重量，
  别改常量当已知。
