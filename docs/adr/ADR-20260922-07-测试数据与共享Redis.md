## 状态
已接受（不 FLUSHDB、不开 db16；改门禁自清 + 推广既有先例）

## 背景
用户提案：申请临时只读权限认键后逐条删，长期改用「临时 Redis 库 db16」并在测试后清理。
现状与实证：本会话四轮里，**连 Redis 的任何动作（含只读枚举 db0、读 db15 单键、删自己的键）都被自动模式
分类器挡下**，所以「临时授权」这条路不总可靠；`REDIS__DB=15` 已是 2026-09-21 13:40 批下来的沙盒口径，
db15 里现有本轮与上一轮的门禁残留（13:1x 读到 9 个键，之后又跑了三轮门禁，只多不少，且我读不到）。
另有一条更省的事实：**9 个门禁文件已经在用 `settings.platform.use_redis = False`**
（`tests/s8_frontend_contract.py:1079` 的注释原话就是「不把测试会话写进共享 dev Redis」）。

## 决策
1. **不开 db16**——那只是把污染换个房间，`heal_running()` 的坑照旧在。
2. **不建常驻清理脚本**（`scripts/` 在本仓不存在，工装进仓就得进索引、得维护）；
   改为**谁建谁清**：用真 Redis 的门禁必须在 `finally` 里删掉自己那几条键（s5 t31/t15、s15 t1 已是这个写法）。
3. 推广 `use_redis = False` 为默认纪律：凡只需 TestClient 的门禁一律不接 Redis，
   确需双通道平价的才显式开（s7 那一类），并把 db 钉在 15。
4. 本轮 db15 残留**不清、不 FLUSHDB**：整库 FLUSHDB 会连带抹掉上一棒留着当样本的会话，
   而「谁留的」这个问题我们现在答不上来。要么逐键（需读权限），要么留给下一棒连同根因一起治。

## 后果
正面：残差不再累积的根因被堵住（门禁不写共享库），且不新增需要维护的工装。
负面：db15 眼下脏着；「按身份删」这条路要有 Redis 读权限才能走通，卡在授权上而不是卡在技术上。
