## 1 · 模块职责与边界

- **`tools/**`**：LangChain `@tool` 造工具、`@register_tool` 登记进 `TOOL_REGISTRY`；文件/终端/搜索/知识库四类工具 + 审批分级表（`_approval.py` 的 `TOOL_TIER`/`ACTION_TIER` 与 `gate_decide`）+ 会话边界唯一判据（`_boundary.safe_session_path`）+ 两级工具召回（`tool_recall.py`）+ 子进程沙箱（`sandbox.py`）+ `libs/`（Editor 复制件 1117 行、常驻 Terminal、git via `gh`、linter、data_preprocess）。

## 4 · 审查发现

### 🔴 P0

🔴 **数据丢失：Editor 异常恢复支路在默认配置下会把目标文件清空**
`codeharness/tools/libs/editor.py:514 _edit_file_impl`：`temp_backup_file`（:562 建，`"w"` 空文件）的原文写入 `writelines(lines)` 只在 :603 `if self.enable_auto_lint:` 块内（:605）发生；而 `enable_auto_lint` 默认 `False`（:109），`editor_tools.py:34` 建 `Editor(working_dir=session_root())` 从不置真——**生产里备份永远是空的**。泛捕获支 `:671 except Exception` 在 :684 执行 `shutil.move(temp_backup_file.name, src_abs_path)`，即「用空备份盖回原文件」。

**为什么**：destructive move 发生在 :598（新内容已替换原文），:598 之前的任何**非 OSError/ValueError/FileNotFoundError**（这三类分别在 :667/:669/:665 被具体支路接住并返回字符串、不动文件）异常落到 :671 → :684 把一个**空文件**移到仍完好的原文上 → 用户整份文件被静默清成 0 字节，且随后 :689 `raise` 只让模型看见 `[错误]`，内容已丢。Linux（部署形态=容器，见 platform-infra F-F）上对已 `shutil.move` 的空 tmp 做 rename 会成功，故是**真数据丢失**而非 Windows 的 PermissionError 挡住。这条安全网本就是为了「restore original」而存在（:661 注释「recover the original file」），但因备份填充被挂在默认关的开关后面，网本身是空的。同族第一性：§2.2「写读同源 / 边界先于昂贵操作」的镜像——恢复路径必须与它要保护的对象同源，这里不同源。

**建议**：把 `temp_backup_file.writelines(lines)` 提到 :598 的 destructive move **之前、且不受 `enable_auto_lint` 约束**（备份原文无条件成立）；或在 `enable_auto_lint=False` 时让 except 支**不做任何 move**、原文件本就没被动过（:598 之前异常时 src 完好，直接返回错误即可）。推荐前者（保持「无论 lint 与否都能回滚」的口径统一，也顺带修掉 :598 与 :605 之间那个极窄的「原文已被新内容覆盖、备份还没写」空窗）。非平凡逻辑需留一格：造 `enable_auto_lint=False` 下 `_edit_file_impl` 抛非具体类异常、断言原文逐字节仍在。

### 🟡 P1

🟡 **召回观测不一致：`search_knowledge_base` 工具不进 `recall_*` 账本、也不参与短路**
`codeharness/tools/__init__.py:96 kb = LongTermMemory(embeddings=LLMGateway.embeddings(), doc_type="kb")`——每次工具调用现建一个**无 `meter=`** 的实例。`LongTermMemory._count`（`longterm.py:102`）在 `meter is None` 时静默跳过；`up` 短路位（:95）是实例级、随对象一起丢。

**为什么**：装配期建的预取 kb/ltm 腿（`team.py:26/198` 带 `meter=`）才有 `recall_failures/recall_zero_hits/recall_returned` 计数与「本场不再尝试」短路（R1/R2 已登记并验）。模型主动走的这条工具腿**两样都没接上**：① 用量页的 `recall_*` 三笔**不含**模型自己发的知识库检索——一场重度依赖 `search_knowledge_base`、Qdrant 挂了每轮都失败的会话，账本仍显示 `recall_failures=0`，把「这条腿坏了」演成「这条腿没被走过」（正是 §1.4 R1 要堵的「静默失败、没人装表」，只是漏在工具腿上）；② 每次调用都重新付 ~2.3s 的宕机往返（`longterm.py:92` 记的现证），预取腿挂一次就短路、工具腿挂 N 次要付 N 次。属「错误降级不可观测」+「判据覆盖不到生产传参形状」。

**建议**：`search_knowledge_base` 从当前会话取现成的 kb 读者（`role_zero.kb`/装配注入的那只带 meter 的实例），而不是每次现建——但注意文件注释 :89 说「每次现建是为绕事件循环绑定」；折中修法：保留现建、但把 `meter`（会话 `CostManager`，可从 `runtime` 或 `io_` 侧取）与一个进程级 `up` 短路位传进去，使计数落账且同场不再反复白等。**先确认口径**：这三笔计数是否本就该只反映预取腿、工具腿刻意不入账？若是，请把理由写进注释并让用量页文案不误导（否则数字面「召回不可用=0」是假话）。

### 💭 P2（≤5）

💭 **审批 fail-open 的窄口：`writes_inside_workspace` 对不认识的路径键名默认放行**
`_approval.py:72-80`：遍历 `_PATH_KEYS=("path","filename","file_name","file_path","dir_path")`，命中第一个非空 str 就返回 `safe_session_path(v) is not None`；**一个键都没有则 `return True`**（:80）。对 `workspace_write` 档工具，若其写路径参数名不在这五个里，会被判成「在工作区内」→ 在 `workspace_write` 会话免审、且路径实际落哪由工具自己 `_safe`/`_inside` 兜。今天注册的工具都用了这五个键（无活体漏），但 `ext_api/tools.py:22` 可注入任意自定义工具、若某件把 workspace 档 + 非列表内路径键组合起来，就是表级 fail-open。与本模块头「认不出的动作一律按需要审批（fail-closed）」（:11-12）取向相反。**建议**：workspace_write 档工具在 args 里**找不到任何已知路径键**时，`required_tier` 升 `full_access`（默认从严），而不是回 `True`。

💭 **`HitCounter.bump` 非原子读改写会丢计数**
`exp_pool/manager.py:45-46 async def bump(...): await self.redis.set(self._key(...), str(await self.get(...) + 1))`——`get` 与 `set` 之间隔着一次 await，同一 user 两个并发激活各自读到 N、各自写 N+1，一次自增丢失。**影响有限**：计数只用于 `query_exps` 排序的 tie-break（`manager.py:77`），Redis 不可用时本就退化为 0/纯相似度。仍建议注明这是「尽力计数」或用 `INCR`（单命令原子）。属「并发与竞态」但后果良性。

💭 **linter「改完自动 lint」在默认配置下是死路；结构守卫只扫两个文件**
- `editor.py:109 enable_auto_lint=False` 且 `editor_tools` 从不置真 → `_edit_file_impl` 的 `_lint_file` 支路（:567/:603）在生产**永不执行**；`linter.py` 整件只被 `t25-28` 直接测到（`_lint_file`），工具面写文件不触发语法闸。`_shims.py:2` 头注称「真 Linter 已让『改完自动 lint』不再是空话」——实现是真的，但接线仍在默认关的 flag 后面。要么在 `editor_tools` 建 Editor 时按配置打开，要么把这句注释改准（与 §1.5「召回语料不是 free place」同理：声称的能力要能通电）。
- `tests/s4_tools.py:1162-1165` 的 t51③「三类文本写调用双钉 encoding/newline」AST 守卫**只 walk `libs/editor.py` 与 `__init__.py`**。`sandbox.py:105 script.write_text(code, encoding="utf-8")`（写 scratch `.py`）带 encoding 无 newline、且不在被扫集合内——CRLF 对 CPython 源无害，但守卫宣称的是「一族按形状找齐」，`sandbox.py` 这个同形状写点落在扫查面之外。建议把 `sandbox.py` 纳入 t51③ 的 `rel` 列表（或显式注释为何豁免）。

💭 **`read_file` 遇非 UTF-8/二进制文件抛异常，与兄弟读口不一致**
