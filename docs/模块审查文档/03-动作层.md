## 1 · 模块职责与边界

动作层 = 经典线（`roles/agent.py` 的 `Agent`）与动态线共用的「一次有语义的工作单元」。每个动作是 `codeharness/base/action.py` 的 `Action`（别名 `BaseAction`，`action.py:44`、`action.py:165`）子类，实现 `async def run(msg) -> Message`，产出物写进 per-session 产物仓 `ArtifactStore`，回流消息带 `instruct_content` + `instruct_schema` 给下游角色。

边界（谁不在这层）：
- **执行/联网本体不在动作里**：`RunCode`/`RunPythonCode` 把子进程、超时、进程树杀、PYTHONPATH 钳制全委托给 `codeharness/tools/sandbox.py`（`run_code.py:73`、`data_analysis.py:25`）；`Research`/`SearchAndSummarize` 的联网腿走工具注册表 `search_internet`（`research.py:21`、`search_and_summarize.py:9`）。动作层只是调用方 + LLM 复盘/汇总。
- **结构化输出的唯一出口在基类**：`Action._ask`（`action.py:91-112`）是全仓 `llm.structured` 的唯一通道（接线台账 #1：`actions/` 下不许再直连），字段级定向重试（`_structured`，`action.py:70-89`）也在这里。
- **审批档位不在动作里**：`ACTION_TIER` 中心表在 `codeharness/tools/_approval.py:53`（刻意「表放这里而不是加类属性」，`_approval.py:9-12`）。
- **装配不在动作里**：动作随角色/团队/SOP 模板传实例列表，无全局动作表（`ext_api/actions.py:3-4`）。
- 不做清单：多模态入参通道（`_aask` 无 `images`，`action.py:65` + `PLAN.md:215-217`）、`_execute_api`（register_tool 独立 API 形态，判「推迟」：出口是任意 `output_pathname`，与 per-session 边界冲突，见 `write_prd.py:9-10`）。

`sop/**` = N7「把源写死的组队变成可存取对象」：`SopTemplate`（模板=装配函数+订阅边）与 `build_team_from_template`（模板→可执行图，`builder.py:15`）。`ext_api/**` = N2 扩展点唯一正门（`register_role/action/tool/template`）。`skills/**` = 源 Semantic Kernel 的功能等价物（一个 prompt 模板文件 + `SkillAction` 装配器，`loader.py:13`）。

## 4 · 审查发现

> 格式依 §4。本轮**未发现 P0**（无确认的竞态/数据损坏/注入越界在已接线生产路径上成立）；§5 量法逐条见第 5 节。

🟡 **正确性：WriteCode 先删工单文件再调模型，模型失败则工单丢失**
`actions/write_code.py:96`：`(store.root / RepoName.DOCS / BUGFIX_FILENAME).unlink(missing_ok=True)`，而真正烧模型的 `_aask` 在 `write_code.py:114`、产物 `store.save` 在 `:116`。

**为什么**：unlink 在生产物落盘**之前**执行。若 `self._aask` 抛（端点 429/半截 JSON 走 gateway 修复仍失败——见 §2.1「异常不许裸吞」），BUGFIX 工单已从盘上消失而 `SRC/filename` 未写；下一轮 `store.get(BUGFIX_FILENAME)`（`:93`）取空 → `feedback=""` → REFINED 分支的「Bug Feedback logs」段被清空，修复上下文不可恢复。这与 C59「审批前副作用被重放」是同一族的**顺序**问题（副作用步早于 productive 步），只是方向相反：这里副作用（删）先于产出（写），产出失败没有回滚。注：因 gate/act 节点已拆（s8 t8 ④），本动作不会被 resume 重放，重放不背这个锅——是「同一次执行内先删后写、写失败即丢」。

**建议**：把 unlink 移到 `store.save(SRC, ...)` 之后（先落产物再消费工单）。源 `write_code.py:163` 同款先删是本仓可改进处，不是必须照搬的死值。

🟡 **越界：ExtractReadMe 从任意绝对路径读文件且档位免审**
`actions/edge_actions.py:25`：`p = Path(fic["readme_path"])` → `:26`：`readme = p.read_text(encoding="utf-8", errors="replace") if p.exists() else ""`；档位 `ExtractReadMe` 在 `workspace_write`（`_approval.py:51`）。

**为什么**：`readme_path` 取自 `msg.instruct_content`（模型可控），未过 `safe_session_path`（写侧越界件复用的唯一判据，`_approval.py:73-79`）。且 `_PATH_KEYS`（`_approval.py:58`）只有 `path/filename/file_name/file_path/dir_path`，不含 `readme_path` → `writes_inside_workspace` 走「不带路径的写类件按表里定的档走」（`:80` 返回 True），越界读**不会**把档位升到 `full_access`。净效果：`workspace_write` 会话里免审地把工作区外任意文件读进 prompt 并入 SPO 图（`edge_actions.py:58-59`），是一类**读侧越界/信息泄露**（§2.2「`..` 越界先拒 C49」的镜像，本件是读不是写所以躲过了写侧判据）。

**待确认**：缺「ExtractReadMe 在当前会话里是否真能被带 `readme_path` 的触发消息装配」的信息——它是 N2 示例件（`edge_actions.py:8`「外部仓库导入是工具面不是会话 SOP」），本轮 grep 未见 `codeharness/` 内装配点；若确不可达则功能面不显形，但作为已注册动作（在 `ACTION_TIER`）其档位语义与副作用不符仍是维护雷。

**建议**：读侧同样走 `_boundary.safe_session_path`，或至少把 `readme_path` 加进 `_PATH_KEYS` 让越界判定生效（与写侧一件不多写、复用同一条判据，符合 `writes_inside_workspace` 注释的「另写一份迟早长歪」）。

🟡 **档位与副作用不一致：ExecuteTask / DebugError / FixBug 过度审批**
`_approval.py:42` 把 `ExecuteTask`、`DebugError` 放进 `_ACTION_FULL`（注释理由「会真跑命令 / 起解释器 / 联网」），`_approval.py:50` 把 `FixBug` 放进 `_ACTION_WORKSPACE`（注释理由「产出 Document / 写工作区文件」）。

**为什么**：三件实际副作用都与档位声明不符——
- `ExecuteTask`（`execute_task.py:8-9`）`run` 是 `pass`，**零副作用**，却被判 `full_access`：任何会话里被派发都要人批一次，批完什么都不发生。
