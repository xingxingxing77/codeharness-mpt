## 1 · 模块职责与边界

- **`provider/`** 是全仓唯一与对话模型通话的出口（`gateway.py:1` 自陈「判定 R1」）：建客户端（`_build`）、单点计量（`ainvoke` 里唯一一次 `add_usage`）、重试归属（`_acall` 一处，SDK 层被 `max_retries=0` 钉死）、结构化输出与 repair 回落管线、以及 FakeLLM/HashEmbeddings 等**测试替身（产品树的公共件）**。它不许做：预算判断、限额、降级重发超时请求（ADR-06 口径，`cost.py:6-7`「没有任何预算判断」）。
- **`configs/`** 是配置真值与**信任边界**：pydantic-settings 吃 `.env`（双下划线嵌套），坏配置一律在构造期当场拒（C5/C27/C34/C48/C64/C28 的 validator 族）。它不许做：静默夹边界、把「设 0」解释成「关掉保护」。
- **`base/`** 是 Action 基类（结构化输出 + **字段级定向重试**的唯一出口 `_ask`，接线台账 #1）与多态序列化 Mixin（源逐字件）。它不许做：直连 `llm.structured`（全仓 structured 必经 `_ask`）。
- **`utils/`** 是源逐字复制件 + 本仓自有文本切裁（`text.py::clip` 带截断标记、`token_counter` 纯本地估算）。边界纪律：计数函数**不许出网**（C79 已收）；零生产调用者的源公开面按 09-27 判例「只记不动」。

## 4 · 审查发现

### 🔴 **正确性（漏账可观测）：structured 腿的超时不落 `_timeout_lost` 账差——C42/C52 同族的第三条腿**
`codeharness/provider/gateway.py:432-434`：
```python
out = await _acall(runnable.ainvoke, prompt, timeout=deadline, **kw)
except Exception as exc:
    self._account(getattr(exc, "output", None) or getattr(exc, "completion", None), tag)
```
对照 `gateway.py:290-295`，`ainvoke` 两条腿的 except 都已接 `_is_timeout(exc) → self._timeout_lost(...)`，而 `_Wrapped.ainvoke` 的 except **没有这一道**：`_acall` 内 `wait_for` 或 SDK 抛的 `APITimeoutError` 在这里既被 `_retryable` 判为不重发（`gateway.py:497-498`），又因异常上无 `output/completion` 而 `_account(None)` 静默返回——**厂商大概率已计费的一发，账上零、日志里连那声可 grep 的账差都没有**。

**为什么**：这正是 C42「超时那一发不落账」与 C52「SDK 先超时的那一发静默成了账上看不见的支出」治过的病，换了第三个入口进来；而第三个入口恰恰是**动态线主路径**（`RoleZero._think → llm_cached_think → structured`，`_apply_compression` 注释 `gateway.py:239-241` 自己数过：306 笔 span 里 think 132 笔）。`_timeout_lost` 的 docstring（`gateway.py:309`）写「同族另两条腿都补过……只有这两支没补」——台账数漏了一支。判据面也同源缺格：s2 的 t15⑤⑥ 钉的都是 `ainvoke`（`tests/s2_gateway.py:579` 起），无任何一格断言 structured 超时留痕。

**建议**：`_Wrapped.ainvoke` 的 except 里加一支 `if _is_timeout(exc): self.outer._timeout_lost("structured", deadline, tag)`（三行，与 ainvoke 两腿同一出口）；判据在 s2 t15 加第⑦格（structured 桩抛 `APITimeoutError` → `gateway.logger` 上可 grep「超时…不进账」）。立 C 号后按 §6 收口姿势走，本档不动手。

### 🟡 **正确性（生产路径断裂）：`File._omniparse_read_file` import 不存在的模块，pdf/docx 的整条兜底链不可达**
`codeharness/utils/file.py:150-152`：
```python
async def _omniparse_read_file(path, auto_save_image=False) -> Optional[str]:
    from codeharness.utils.omniparse_client import OmniParseClient
```
`codeharness/utils/omniparse_client.py` **不在仓里**（`ls` 实测零命中；`grep omniparse plan/*.md` 零登记）。import 位于函数头、`base_url` 未配守卫（`file.py:158-160` `if not base_url: return None`）**之前**——于是 `_read_pdf`（`file.py:132`）与 `_read_docx`（`file.py:144`）里「先试 omniparse、拿不到 return None 再落 PDFReader / read_docx」的设计意图整体失效：任何一次 pdf/docx 读取直接抛 `ModuleNotFoundError`。生产调用点：`tools/libs/editor.py:144` `content = await File.read_text_file(path)`（读 pdf 可达性取决于 `get_mime_type` 那台 `file --mime-type` 在不在，见 common.py:911——Linux 容器在，Windows 走 "unknown" 分支反而返回 None 空块）。

**为什么**：判 `弃`（omniparse 不搬，`_config_compat.py:6` 注释）之后调用点没同批改——「没搬的依赖」残留成 import，把**还活着的兜底**（llama_index PDFReader、`read_docx.py`）压死在它身后；破的是「函数先守后重」的同族纪律（C39/C47：边界判定先于大开销操作）。异常会被 `Agent._act` 的「抛错回喂」吸收所以不是会话级事故，但工具面从此读不了 pdf/docx 且报错文案是 `No module named`，模型会被引去重试同一路径。

**建议**：最小修法是把这个 import 挪进 `base_url` 守卫之后（或整函数体 try/except ImportError 视同未配置回 None）；更省的做法是照判定把 `_omniparse_read_file` 整段删掉、`_read_pdf/_read_docx` 直连本地兜底（omniparse 已判弃，留着这段本身就是第三种状态）。另立 C 号；判据建议：s4 加一格「editor.read 一个真 pdf 不抛 ModuleNotFoundError」。

### 🟡 **数据丢失（降级档里再切一刀且不留痕）：`llm_repair_json` 把坏输出截到 4000 字再让模型自修**
`codeharness/provider/repair.py:440-441`：
```python
fixed = await llm.aask(JSON_REPAIR_PROMPT.format(
    json_data=raw[:4000], json_decode_error="invalid json"), tag="json_repair")
```
生产调用点两处：`roles/agent.py:211`（ActionChoice 兜底）、`roles/role_zero.py:399`（ZeroThought 兜底）。超过 4000 字的坏 JSON 被**无标记**截尾送修；模型对着半截文本补出合法闭合、`repair_to_model` 校验通过（thinking 模型的 ZeroThought 正文常远超 4000 字）——**尾部内容丢了，调用方拿到的是「修复成功」**，只有一条 repair warning（`gateway.py:409`），不说输入被切过。

**为什么**：这正是本仓刚为同类形状立过账的族——`text.py:157-174` 的 `clip` 就是「被切的正文此前看不出被切，模型会把半截当全量下结论」修出来的（rag-knowledge §1.5 nested_claim 那轮把「链上留痕只承认真上一站」都补了）。此处是同一纪律的未覆盖点：**修复档吃进截断输入却产出「完整对象」的读数**。另外 `json_decode_error="invalid json"` 是对 prompt 模板的假填值（真错误串没传进来）。

**建议**：`json_data=clip(raw, 4000)`（`clip` 就住在本仓 `utils/text.py`，带「…[已截断，原长 N 字]」标记，零新依赖）；修复成功且 `_raw_len(raw) > 4000` 时 warning 一句「repair 输入被截断，产出可能缺尾」。**待确认半格**：真实产线 ZeroThought 坏输出的长度分布没量过（缺一条 `manual_*` 读数的话这格按「先量后动」补量）。

### 🟡 **静默失败：`_count_tokens_direct` 的 except 无日志回落 `len//4`，压缩闸可在 tiktoken 不可得时整体休眠且零痕迹**
`codeharness/provider/gateway.py:118-124`：
```python
        except Exception:
            # 降级：按字符数/4 估算
            tokens = len(content) // 4
```
这是 `_apply_compression`（`gateway.py:251` `if self._count_tokens_direct(msgs) > keep_token`）与 `_compress_messages` 预算的**唯一计数源**。tiktoken `get_encoding("cl100k_base")` 在无缓存、无网的首次调用会抛——之后每一次计数都静默走 `len//4`，而中文约一字一 token，**估低约 4 倍** ⇒ 显式配置了 `LLM__CONTEXT_LENGTH` 的会话里 C65 刚接好的闸可能永不触发，且日志里一个字都不出。

**为什么**：与 `cost.py:123-126`「漏账必须可见——有 warning 才有可 grep 的账差」同纪律；也与 C41/C51「except 吞成静默降级」同形状。C65 的未验边界只登记了「tiktoken 对 step-3.5-flash 只是近似（估宽不估准）」（`plan/model-gateway.md` C65 行）——登记的是**精度**，没登记这条**降级路径不可见 + 中文方向估窄（不是估宽）**的形状。`_truncate_tokens` 的 except（`gateway.py:137-138`）同款无声。另外该 except 分支没有任何判据（门禁全在有 tiktoken 的机器上跑，这条 fallback 是判据覆盖不到的生产形状）。

**建议**：最小修——except 里 `logger.warning` 一声（带 model/tag），最好进程级只喊一次；判据可在 s13 加一格「monkeypatch `get_encoding` 抛错 ⇒ 有一行可 grep 的降级 warning」。措辞方向若求稳，中文场景 `len//4` 换成 `len//2` 或按 CJK 计数是另一件（先量再说）。

### 🟡 **资源生命周期：`utils/redis.py` 的实例契约与 `brain_memory` 的「每往返新建一个 Redis()」叠成连接池泄漏**
`codeharness/utils/redis.py:26-38`（`_connect` 每次实例各自 `from_url` 建客户端）＋ 消费方 `codeharness/memory/brain_memory.py:85/96`：
```python
v = await Redis().get(key=redis_key)
await Redis().set(key=redis_key, data=..., timeout_sec=timeout_sec)
```
`loads/dumps` 每次调用 new 一个 `Redis`，其 `from_url` 惰性池随首个操作建连，**用完无人 `close()`**（`redis.py:65` 的 close 只由显式调用触发，这两个点不调）。`exp_pool/manager.py:32` 是每个 manager 持一份，形状正常。

**为什么**：长驻服务里记忆腿每存每取都留下一个不复用的连接池等 GC——是 C34 那条「这条腿没有上限」审过的同族「继承来的默认生命周期」问题，只是这次在连接侧。**待确认**：泄漏速率与 GC 兜底效果没有活体 fd 计数读数（缺：小跑一场后 `psutil` 数 TCP 连接的现证）；连接是否即时回收取决于 redis-py asyncio 的 `__del__` 行为，本档不替它下结论。

**建议**（落点二选一，推荐前者）：① `utils/redis.py` 加一个模块级 `get_redis()` 进程共享实例（loop 变化仍由 `_connect` 现有重建逻辑兜住）；② 只改 `brain_memory.py` 让实例随对象/模块持有。修法落在消费方一处即可，但契约（「这个类是按长驻实例用的，不是按调用用的」）写进 `utils/redis.py` 头注释才算还清。
