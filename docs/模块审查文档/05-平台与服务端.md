## 1 · 模块职责与边界

这是**多用户 agent 平台的 HTTP 服务层与平台适配层**，FastAPI 装配 + Redis(可选) + sqlite checkpoints + SSE。

- `server/**` 是 Web/REST/SSE 门面：会话注册表（`sessions.py`）、事件总线进程内实现（`events.py`）、鉴权与账号边界（`auth.py`）、LangGraph 团队图的驱动（`runner.py`）、REST 路由（`api/**`）、中间件与静态挂载（`app.py`）。
- `platforms/**` 是**包外平台适配器**（`platforms/__init__.py:1-6` 明确「内核零 Redis 依赖，全部注入发生在 server 装配」）：会话态 / 事件流 / 插话队列 / 审批台账 / 配额 / trace 六条接缝的 Redis 化实现。feature flag `settings.platform.use_redis` 决定走 Redis 版还是退回进程内版；**默认（无 Redis）走 `server/` 里的进程内实现**。
- 部署面定义运行形态：`Dockerfile` 钉 `--workers 1`、`docker-compose.yml` 里 redis/qdrant 强制密钥、`frontend/nginx.conf` 反代 `/api` `/workspace` 并配 SSE 不缓冲。

**关键边界（一票否决护栏，实测在位）**：多 worker **明确不支持**（`plan/PLAN.md` §7「不做分布式」+ C10「登录态不跨 worker」；`docker-compose.yml:31` 与 `Dockerfile:26` 都钉 `--workers 1`）。本审查里凡是「跨 worker」形状的隐患，都按这条已知天花板读，不另立 P0。

内核（`codeharness/**`）不在本面。runner ↔ 内核只经七个 ContextVar + 一个 `CostManager` + 一个 `APPROVAL_IO` 鸭子接口相连（见 §3）。

## 3 · 对外接缝

### 3.1 REST 路由清单（前缀 `/api/sessions` 除非另注）与各自鉴权/上界

**鉴权统一入口**：所有业务路由过 `Depends(current_user)`（`sessions.py:174-188`）。auth 关（默认）恒返回 `"default"`、不校验；auth 开时校验 Bearer / `?access_token=`，越权一律 **404 不泄露存在性**（`_owned` `sessions.py:242-250`）。

- 会话 CRUD：`GET ""`（auth 开按 user 过滤 `sessions.py:132-133`）、`POST ""`（字段上界 + 唯一性 + 限流，见下）、`GET/PATCH/DELETE /{sid}`、`POST /{sid}/goal[.../complete|/clear]`。
- 运行控制：`POST /{sid}/start`（并发配额 `sessions.py:308-315`）、`/stop`、`/chat`（`send_to≤64`、目标须在 `s.roles` `sessions.py:332-333`）、`/human-input`（`content≤64000`）。
- 反馈：`GET/PUT/DELETE /{sid}/feedback`（key≤80、vote∈{like,dislike}）。
- 成员：`GET /{sid}/tools`、`POST /{sid}/roles`（仅 dynamic、档位校验 `sessions.py:517-522`）、`DELETE /{sid}/roles/{name}`、**`GET /{sid}/roles/draft`（见发现 🟡-4）**。
- 分叉/队列：`POST /{sid}/fork`（`MAX_FORK_FILES=2000` `sessions.py:403`）、`GET /{sid}/queue`、`DELETE /{sid}/queue/{qid}`。
- 回放：`GET /{sid}/graph`、`GET /{sid}/trace`、`GET /{sid}/checkpoints[/{id}]`（只读重建 `register=False` `sessions.py:658,679`；单份 >4MB→413 `sessions.py:694-696`）。
- 工作区：`GET /{sid}/workspace/files`（resolve+深度8+预算2000）、`/file`（预览 5MB、`is_relative_to` 判边界）、`POST /{sid}/workspace/import_repo`（归属判定先于读 body）、`/upload_kb`（20×20MB、读前上限）、`DELETE /{sid}/workspace/kb_doc`（只取 basename）。
- 审批：`GET /{sid}/approvals`、`POST /{sid}/approvals/{aid}/respond`（`outcome∈{allowed-once,rejected}`）。
- 无 `current_user` 的只有两处：`GET /api/health`（脱敏读数）、`/api/auth/*`。静态：`/workspace/*` 经 `guard_workspace`（storage 一律 403，auth 开需 token `app.py:150-157`）、`/` 前端 dist。

**入口 body 上界（两道）**：① 中间件 `guard_body_size` 只看 `Content-Length`、按 content-type 分档（JSON 2MB / multipart 416MB），读进内存之前拒 `app.py:131-141`；② 字段级 pydantic `MAX_*_CHARS`（`sessions.py:19-23`）。二者独立（C86 m38 已验），但见发现 🟡-2：`Content-Length` 缺失时第一道不触发。

### 3.2 SSE 事件通道

- 活流 `GET /{sid}/events`（`sessions.py:586-610`）：`StreamingResponse`，先 `to_thread(bus.history)` 回放、再 `while True: q.get()`；15s 超时发 keepalive；`X-Accel-Buffering: no` + nginx `proxy_buffering off` 才不缓冲。经 `current_user`，auth 开可 `?access_token=`（EventSource 发不了 header 的已知代价）。
- 有界回放 `GET /{sid}/events/history`（sync def `sessions.py:700-717`）：任何要「读完再走」的消费方必须用它，`while True` 的活流会挂死 TestClient。
- 游标契约：`cursor = pad_eid(stream id)` / `cursor_of(seq)`，定宽补零使字典序==数值序；前端只认 `cursor` 去重（`seq` 在 Redis 溢出 float64）。

### 3.3 runner ↔ 内核边界

`_session_ctx`（`runner.py:669-709`）在每次跑图/resume 时装七个 ContextVar：`SESSION_ID`/`CURRENT_PROJECT`/`CURRENT_SESSION`/`REPORT_SINK`/`CHAT_SINK`/`CURRENT_USER`/`PERMISSION`，并把 `APPROVAL_IO` 设成 `ledger_for(sid)`（内核只认 sid/decision/request，零 server/redis 依赖）。取不到会话时 `PERMISSION` 兜 `readonly`（fail-closed `runner.py:697`）。`REPORT_SINK` 是内核块进总线的唯一通道（`_make_sink` `runner.py:643-667`），`astream_events` 只翻译 LLM token 与 interrupt，其余块事件全来自报道槽。

### 3.4 `_JSON_FIELDS` 序列化契约（grep 实证）

`session_store.py:25` `_JSON_FIELDS = {"llm_override":{},"cost":{},"roles":[],"role_defs":[],"feedback":{}}`——Redis HASH 把一切 `str()`，故 list/dict 字段必须在此登记走 JSON，否则回读 `Session(**d)` 会 `str(list)` 炸（`sessions.py:37-42` 的两处注释明确要求「新增字段必须同批登记」）。当前 `Session` 的容器字段（llm_override/roles/role_defs/feedback/cost）**已全部覆盖**，无遗漏。但该契约是**纯注释守着的**，见发现 💭-1。

## 4 · 审查发现

### 🔴 P0-1 · 并发/资源：进程内事件总线的 SSE 订阅队列**仍是无界**（C90 只补了 Redis 版）

`server/events.py:111`：`q: asyncio.Queue = asyncio.Queue()`（无 `maxsize`），`publish` 侧 `events.py:87/89` 直接 `q.put_nowait(ev)`，无丢弃、无计数、无告警。
对照 Redis 版 `platforms/event_store.py:197` `asyncio.Queue(maxsize=MAX_SSE_QUEUE)` + `:216-226` 满了丢最旧 + `[sse-drop]` 计数。

**为什么**：C90 立号的原文症状就是「客户端停止消费时 `put_nowait` 持续堆积，堆到进程内存里，且没有任何计数器或告警（ring 那半有 `_RING_MAX` 上限、这半没有）」。修的时候只改了 `event_store.py` 的 Redis 实现，`SessionEventBus.subscribe` 那半**仅按 C90 ③ 改成了 async 以求接口同形**（`events.py:107-109` 注释自述「本实现无 I/O，async 只是形状」），队列有界这件事没一起做。而 `app.py:74-76` 表明**无 Redis 时默认走 `SessionEventBus()`**——即最常见的单机部署形态恰恰是被漏掉的那一条。一条后台标签页/断线未回收的连接，就能把这场会话的未消费事件无限堆进内存。这正是 C90 的资源型 P0，只是搬到了另一条实现路上（「修一族要按形状找齐」）。

**建议**：给 `SessionEventBus.subscribe` 同样上 `maxsize`（复用 `event_store.MAX_SSE_QUEUE` 或新常量），`publish` 侧 `put_nowait` 包 `QueueFull` → 丢最旧 + 计数告警，与 Redis 版逐字同形。判据落 `tests/s7_platform.py`：C90 的 t21 目前是「redis 套件、真 `RedisEventBus`」，**从没断言过进程内 bus 有界**——补一格对 `SessionEventBus` 灌 `MAX+50` 条不消费，断言队列恰好 `MAX`、队首被丢、有 `[sse-drop]`。

### 🟡 P1-2 · 安全边界：入口 body 闸可被 chunked / 缺 `Content-Length` 绕过

`server/app.py:132-134`：`guard_body_size` 只在 `request.headers.get("content-length","").isdigit()` 为真时才判上限，`:129-130` 注释称「缺失 Content-Length 时放行……JSON 端点还有 pydantic 兜着——两档都不至于无界」。

**为什么**：那句「不至于无界」不成立。字段级 pydantic `MAX_IDEA_CHARS`（`sessions.py:27`）是在 Starlette **把整段 body 读进内存并 `json.loads` 之后**才校验的；`await request.json()` / `request.body()` 本身没有字节上限。攻击者只要用 `Transfer-Encoding: chunked`（或干脆不发 `Content-Length`）POST 一个几百 MB 的 `idea`，中间件那一档 2MB 就**永不触发**（`length` 非数字 → 直接 `call_next`），大 body 照样整段进内存，pydantic 只是在读完之后才 422。C86 立号的核心价值「挡在读进内存之前」被一个头部选择整个绕开——这与 C39/C86「边界判定先于大开销操作」是同一纪律的破口（m38 只验了「摘中间件后 pydantic 仍接住」，没验「chunked 时中间件根本不参与」这一支）。

**建议**：给 JSON 类请求加一道「读流计数」的硬闸——包 `request.stream()` 累计字节、超 `cap` 立即 413，而不是只信声明的 `Content-Length`；或在中间件里对「有 body 方法（POST/PUT/PATCH）但无 `Content-Length`」直接拒绝/改走带上限的读取。落 `s7` 一格：不带 `Content-Length`、chunked 发 >2MB JSON → 必须 413。

### 🟡 P1-3 · 并发/自愈：`heal_running()` 的「多 worker 幂等」docstring 与实现不符（共享库下会掐掉别人正在跑的会话）

`platforms/session_store.py:131-139`：`heal_running()` 遍历 `zrange(INDEX,0,-1)`，**无条件**把每一条 `status==running` 改成 `stopped`。docstring 写「多 worker 时只应在启动时跑一次」「多 worker 各自启动时都跑一遍，幂等」。`app.py:63` 在 lifespan 里对每个进程都调它。

**为什么**：Redis 是**全 worker 共享的一份状态**。当 worker B 启动跑 `heal_running()` 时，它看不到「哪条 running 正被 worker A 的活任务持有」，会把 A 正在跑的会话一起标成 `stopped`——而 A 的协程还在往这条记录合流。docstring 把它说成幂等且多 worker 安全，是**主动的错误承诺**（对照 `AGENTS.md` 护栏：门禁里的 `create_app()` 会 `heal_running()` 掐掉别人正在跑的那一场——同一条危险语义）。今天就打不到的唯一原因是 `--workers 1` 被 `Dockerfile:26`/`compose:31` 钉死、且 §7「不做分布式」；所以这是**已知天花板内的文档失真 + 潜在雷**，不是当下线上事故。

**建议**：二选一——(a) 把 docstring 的「多 worker 幂等/安全」删掉，如实写「仅单 worker 成立；共享 Redis 多 worker 下会误停他人 running，须先给 running 加 worker 归属租约才可放开」；(b) 若确有共享库多进程形态，running 记录里落一个 owner（worker pid/心跳），`heal_running` 只回收 owner 已消失的条目。倾向 (a)，与 C10 那轮「把不跨 worker 写进契约、停止当 bug 追」的收口姿势一致。

### 🟡 P1-4 · 只读路径有副作用/花费：`GET /{sid}/roles/draft` 在 GET 里真调模型

`server/api/sessions.py:558-573`：`@router.get("/{sid}/roles/draft")` → `draft_role` → `await draft_role_profile(llm, ...)`，对 LLM 端点发起一次真实生成。

**为什么**：违反 §2.3 清单「只读路径不许有副作用（装配、写库、占表）——C43」的精神：GET 不仅做外部网络副作用，还是**花钱的操作**（`AGENTS.md` 护栏「花钱的验收先问」）。GET 语义下浏览器预取、链接爬虫、重试都会触发，且无幂等/成本闸——一次点按或一次 prefetch 就是一笔真模型开销。它不落库（只有 `POST /roles` 落），所以危害限于「非预期花费 + 长耗时挂在读动词上」，判 P1 不判 P0。

**建议**：改 `POST /{sid}/roles/draft`（草案生成是「让服务端产出一份新内容」，本就是命令语义），前端对应调用点同步；若要防刷，给它挂 `quota` 那同一条按 user 的限流。

### 💭 P2（≤5 条）

**💭-1 · 契约脆弱：`_JSON_FIELDS` 靠注释登记，无自动守卫。** `session_store.py:25` + `sessions.py:37/41` 两处注释要求「新增 list/dict 字段必须同批登记 `_JSON_FIELDS`」。当前齐全，但下一枚容器字段（如再往 `Session` 加一个 list）漏登记时，进程内仓正常、Redis 仓 `str()` 落库回读炸——两仓不同形（C31/C89 同族形状）。**建议**：加一格测试：反射 `Session.model_fields` 里所有 `list`/`dict` 类型字段名，断言它们全 ∈ `_JSON_FIELDS`。一劳永逸替代「靠人记得」。

**💭-2 · 可观测性：`_reader` 吞掉 XREAD 全部异常、静默 0.5s 轮询永不喊。** `event_store.py:208-210` `except Exception: await asyncio.sleep(0.5); continue`，无日志。**为什么**：订阅侧若因鉴权变更/键被删/持久错误一直失败，会无声空转，用户只见 SSE 不再更新、日志零痕迹（对照 `_flush_loop` `:132` 老老实实 `logger.warning`）。**建议**：与 `_flush_loop`/`_listen` 同款——首次或每 N 次失败留一行可 grep 的 warning。

**💭-3 · 泄漏面：`_fail` 把完整 traceback 推进事件流给前端。** `runner.py:832` `bus.publish(sid, kind="error", value=traceback.format_exc(limit=6))`。**为什么**：会话事件流经 `_owned` 只有属主可见（auth 开），单机态可接受；但内部文件路径/依赖栈出现在 UI 错误卡上，多租户语境下是信息泄露的边角。**建议**：事件流只放 `type(exc).__name__: str(exc)`（给用户的），完整栈只 `logger.error`（`[session-failed]` 那行 `:830` 已经在记）——两个受众各取一份。

**💭-4 · 进程内台账 `_MEM` 无回收。** `approval_store.py:121,140`：`_MEM.setdefault(sid, InProcessApprovalStore(sid))` 只增不减，会话删除/收口都不摘；无 TTL（`InProcessApprovalStore` docstring 自述「生命周期跟随进程」）。**为什么**：单进程短生命周期下量小可接受，但长跑服务里每个曾触发过审批的 sid 永久留一份 dict——与会话删除不同步的轻泄漏。**建议**：`runner._forget(terminal=True)` 收口时把 `ledger_for` 的内存档一并摘；或在 `_MEM` 上做一次有界 LRU。

**💭-5 · 配额/并发上限在无 Redis 档整体静默失效。** `app.py:69` 只在 redis 分支装配 `quota`；`sessions.py:141-146`（create 限流）与 `:308-315`（`max_concurrent`）都以 `if q is not None` 为门。默认单机部署 = 无建会话限流、无并发会话上限。**为什么**：这与「auth/rate 只在 redis 有意义」是同一档边界，但读数处没有任何一行说明「这台没配额」，容易让人以为限流已生效（C10 那轮教训的翻版：文档说开了、其实没开）。**建议**：`/api/health` 里带一个 `quota_active: bool`，或在无 redis 启动时留一行 warning，把这条边界显式化。
