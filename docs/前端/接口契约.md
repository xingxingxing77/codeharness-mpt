# 前端 ↔ 后端 接口契约

> 前端不是独立站点：**同一个 FastAPI 进程**用 `StaticFiles(html=True)` 挂 `frontend/dist`。
> 所以「前端能调什么」完全等于「后端路由表有什么」，而这张表由 `tests/s8_frontend_contract.py`
> 逐条比对，不靠人记。改任何一端前，先读第 6 节。

`/api/health` → `{ok, llm_configured, llm_problem, model, base_url, api_key_masked, auth_enabled, workspace_root}`。
前端用两件事：**`auth_enabled` 决定要不要登录页**（不是调 `/api/auth` 探的），
`workspace_root` 用来把绝对产物路径换成 `/workspace/...` 可点链接（`store.workspaceUrl()`）。

`/api/models` → 把端点侧 `GET {base_url}/models` 摊平成名字列表，`current` 是配置里的默认模型
（ollama 那种 `名字:latest` 会归一回配置的写法，好让菜单的勾选落得准）。服务端缓存 30s。
**`ok=false` 不是故障**：没配 key、端点不实现 `/models`、网络不通都走这里，前端据此把模型位
退化成只读文本——不画一个点开是空的箭头。

`import_repo` 的两条 400 不在上面那六条里，判据在 `server/api/workspace.py`：`repo_path` resolve 后
不是已存在的目录 → 「repo_path 必须是已存在的目录」；不在 `workspace_root`（各会话目录的父）内 →
「repo_path 必须在 workspace_root 内」，用 `is_relative_to` 而不是 `startswith`（后者会放行兄弟目录）。
界面把服务端原文原样显示在文件树上方的红字行，失败不当成功。

`upload_kb`（C3）的门口三判也在这个文件里，且**都在读文件之前**判完：文件名只取 `Path(name).name`
（`../../evil.md` 到这里塌成 `evil.md`，落点再用 `is_relative_to(kb/)` 复核一道）、后缀必须在
`{.txt, .md, .docx, .pdf}`（白名单住在 `codeharness/actions/upload_kb.py::SUPPORTED`，端点 import 它，
不两处各抄一份）、单文件 >20MB 或一次 >20 个 → 400。原件落 `<会话工作区>/kb/`（`GET /workspace/files`
本来就扫整棵目录树，前端不加代码也看得见），随后**以那份盘上文件**为输入走 `UploadKB` 切块入库。
被拒的那条进 `errors[]` 并带原因，其余照常摄取——「默默灌半截」和「一个坏文件赔上一整批」都不是这里要的结局。

**向量服务连不上 → 503**（C16）：这一步在**原件已落盘之后**，所以「失败」和「东西去哪了」必须一起说。
`detail` 是三行文本（`req()` 原样翻成 `Error.message`，`.kbMsg` 是 `pre-line` 所以分行照显示）：
连不上的是哪台与真实失败形状、**已写进 `kb/` 的 N 份原件没有切片**（逐份点名）、重传即可并给出该查的
`QDRANT__URL` / `EMBEDDING__BASE_URL`；门口判掉的拒因同批带上（另起一句「与向量库无关」），不被降级文案盖掉。
判据不是「异常一律降级」：端点顺 `__cause__/__context__` 链只认**连接级**失败（`httpx.ConnectError` / 内置
`ConnectionError`），其余异常照旧 500——把真 bug 翻成「服务不可用」的谎比一句 500 更糟。超时（服务在但很慢）
今天仍走 500，口径未定，别顺手并进来。

## 2. 请求体与「哪里会 422」

```python
CreateSessionReq: idea(必填 min_length=1) · project_name="" · n_round=5
                  paradigm="classic" · sop="" · llm={"model": "..."}   # 只有 model 生效
                  permission="readonly"                                  # 免审档，见第 7 条
ChatReq:          content(必填) · send_to=""        # 空=这场的 entry_role，填角色名=直聊
RoleReq:          name · profile · goal(三者必填) · constraints="" · tools=[]   # /roles 招人（§2 第 8 条）
HumanInputReq:    content(必填)
PatchSessionReq:  idea? · archived? · pinned? · permission?   # 四字段全可选
```

七条会咬人的校验，都在 `server/api/sessions.py`：

1. `paradigm` 只吃 `classic|dynamic|react`，其余 422。
2. `sop` 非空时 **create 当场**查模板名，拼错立刻 422 —— 故意不拖到 start 才炸。
3. `project_name` 不能含路径分隔（`Path(v).name != v` 即 422）：它直接拼成
   `workspace/{name}`，是会话目录、产物仓和前端文件树共同的根，带分隔就能越界。
4. `PATCH` 四字段全可选、不传保持原值，所以**取消归档必须显式发 `archived=false`**。
5. `llm` 是会话级模型覆盖，**只认 `model` 一个键**（其余键忽略）：`base_url`/`api_key` 若也吃
   客户端输入，等于让请求方指定任意端点（SSRF 面）。生效点在 `codeharness.team._make_llm`，
   `server/runner.py::_prepare` 三条装配线共用它建的那一个网关实例。
6. `/chat` 的 `send_to` 必须是 `session.roles` 里的真节点名，否则 422 并回列出可选项。
   为什么必须在入口挡：`team_graph.py:127` 对未知目标是 `if recv in agents:` **无 else**——
   不投递、不报错，前端只看到 200。`roles`/`entry_role` 由 `runner._prepare` 从真装配回填，
   **建会话时为空**，所以空 `roles` 的老会话不触发这条校验（也就没有可承诺的目标）。
7. `permission` 只吃 `readonly | workspace_write | full_access`，语义是**免审范围**：动作需要的档位
   高于会话档，就在 `gate` 节点（`role_zero._gate_commands` / `agent._gate_action`）挂起等审批。
   判定表在 `codeharness/tools/_approval.py`（工具与 Action 逐个显式定档，认不出的按 `full_access`）。
   回执走 `POST /approvals/{aid}/respond`，`outcome` 只有 `allowed-once` 与 `rejected` 两个值，
   **首个回执生效**、后来的改不动；`aid` 未知 → 404。
8. `/roles` 招人（C1-③）四条闸，全在一个出口里判（`codeharness.team.check_role_def` + `required_tier`）：
   ① 只有 `paradigm=dynamic` 且没走 `sop` 模板的会话能招 → 否则 422，理由会写在文本里
   （classic/react 线没有任何路由会点名新节点，招进来就是个醒不过来的死成员，宁可不收）；
   ② 会话 `running` → 409：**生效点是下一次起跑/续跑的装配，不做图中热插**（LangGraph 的节点集
   在 compile 时就固定），响应里因此带 `takes_effect:"next_start"`；
   ③ `name` 必须字母开头、≤32 字符、不与已装配重名（它同时是 LangGraph 的节点名）；
   ④ `tools` 每个名字都要存在于 `TOOL_REGISTRY`，未注册 → 422 并点名是哪几个（悄悄丢掉 = 装配出来的
   角色不是请求的那个角色）。另外**声明的工具要会话档罩得住**：查的是执行期那同一张
   `_approval.TOOL_TIER`（表里没有的按 `full_access`），要 `full_access` 而会话是 `readonly` → 422 并说要哪档。
9. `/roles/draft` 只回草案、不落库（现场产 profile 的那一半：structured 出口给 `RoleDraft` 六字段）。
10. **目标三条（B5）的口径**：单条字符串、由用户填；`objective` strip 后为空即 422；
    「没有目标」时点完成 422；改目标会把 `goal_done_at` 清回空（完成是针对**那条**目标的，
    换了目标还挂着已完成是假状态）；重复点完成**幂等**（不刷新时间戳、不重发事件）。
    内核侧（`codeharness/**`）**一个字都不许出现** `goal_done_at` —— 这条由 `s8 t17` 钉着，
    不是靠自觉。
   模型声明了注册表外的工具 → **502**（上游产出不合规矩，不是用户输入错），模型端点不通 → **503**；
   要真招人仍然必须 `POST /roles`，第 8 条那四闸一条都不能绕。

11. **队列两条（B6）的口径**：插话**只在节点边界生效**（`team_graph.route` 每轮 `drain`），
    所以「投进去立刻影响当前这一步」这种期待是不成立的；`GET /queue` 只列**还没被取走**的，
    被取走 = 已投递进这一跑，此时再 `DELETE` 拿 404（detail 写清两种可能）。
    队列的增删留痕由队列自己发（`on_change` 接缝在 `server/runner.py::_make_chat` 装上），
    前端那份 `store.queue` 只是投影：开/切会话用 `GET /queue` 对齐一次，其余靠 `kind:"queue"` 事件，
    **撤回失败(404)时也必须再对齐一次**——活流断档期间的事件按游标丢掉，不补这一次就会
    把胶囊挂在一条已经不存在的插话上（活体实测到，`QueueDock.vue` 的 catch 里那两行钉着）。
14. **反馈（B4）的口径与两个坑**：票打在**尾行块键**（`t:<块键>`）上，真值是 `Session.feedback`
    那张表 —— 它是 dict 字段，**必须同批登记 `platforms/session_store.py::_JSON_FIELDS`**
    （漏登记的后果由 `t22` 的反向验证现过一次：不是断言红，而是当场
    `ValidationError: 1 validation error for Session`，正是 §3 那条「存进去读不出来」的形状）。
    同票再点=取消、改票=覆盖，两条都**幂等**：没变化就不发事件（活流里不留空痕迹）。
    参照系的 compare-and-set 版本号**没做**（我们这张表 last-write-wins，前端不假装乐观并发）。
13. **招人表单的可选项只有一个来源（B9）**：`GET /{sid}/tools` 把 `TOOL_REGISTRY.all()` 与
    `team.required_tier` 那张表投影给前端，**前端不抄第二份清单**（抄了就长成「两套表必须互洽」那族洞）。
    ⚠ `required_tier` 吃的是**一批工具名**取最高档，单件要包成列表——传字符串会按字符迭代、
    每个字符都不在 `TOOL_TIER` 里 ⇒ 18 件工具全按 fail-closed 判成 `full_access`
    （本端点第一版就中在这里；`t21` 那条「档位读数不许 18 件全同档」抓的正是它）。
    招人回执 `takes_effect:"next_start"`：LangGraph 节点集在 compile 时固定，不做热插。
14. **摘成员（B9 余账）只认「招进来的」这一族**：`DELETE /{sid}/roles/{name}` 的名单是 `role_defs`，
    不在册一律 **422**（不给 404——404 会让人以为再试一次就有）并回显在册名单。三条闸：
    ① 静态角色（`TeamLeader`/`Alice`/`Bob` 来自装配表）**摘不掉**——摘了 SOP 路由会指向不存在的节点，那场会话直接坏，不是"少个人"；② 运行中 409，生效点是**下一次起跑/续跑**（`takes_effect:"next_start"`，与招人同档）；
    ③ 摘的同时把名字从 `session.roles` 里去掉——`roles` 由装配出口回填（`runner._prepare`），不一起改就会「下拉里挂着已经不存在的人」，而且 `check_role_def` 的 `taken` 也当他还在册，**同名再招会被永久拒**。门禁 `tests/s23_hire_role.py::t7` 四格。
    历史消息里那个 `sent_from` 名字**不会消失也不该消失**——它是既成事实，摘成员改的是装配，不是日志。
12. **分叉（B3）的两条硬要求**：① 新会话**自己发号**——搬历史只搬内容，`seq`/`cursor` 由新会话的
    总线重新派生（进程内那台每台从 1 起号、Redis 那台是 ms 级全局号，所以「游标值不相等」在两台上
    不是同一个判据，判据写成**两条流互不串台**）；② **产物目录独立**——`workspace/{新 sid}/` 整份
    从源目录拷过来，`Docs` 块里的路径按各自 workspace 解析。
    `from_cursor` 是**含端点**的（那一轮本身要留在分叉里），不在流里则 422。
    总表里那条 `copied_files` 只是回执，别当上限用：源目录多大就拷多大（没做截断）。
## 3. 对象形状

`Session`：`id · idea · project_name · n_round · paradigm · sop · user_id · status ·
llm_override · roles · role_defs · entry_role · permission · workspace · error · cost · created_at · started_at · finished_at ·
goal · goal_done_at`
（`archived`/`pinned` 由 PATCH 路由提供；`roles`/`entry_role` 由 `runner._prepare` 在装配完成时回填，
**建会话时为空**，所以老会话与未跑过的会话拿不到角色名。
`role_defs` 是**现场招进来的成员的完整档案**（`[{name, profile, goal, constraints, tools[]}]`）——
`roles` 只有名字，装配要吃档案，所以两个字段并存：`_prepare` 把 `role_defs` 并进 `agents` 之后
`roles` 自然会带上他们，**前端直聊下拉因此零改动就能选到新成员**。
⚠ 这类「dict 列表」字段必须登记进 `platforms/session_store.py::_JSON_FIELDS`，否则 Redis 那台 store
会 `str()` 落库、回读时不是变形就是炸（两台 store 长得不一样是本仓反复踩的那类洞；门禁 `s23 t3` 钉着）。`permission` 新建默认 `readonly`，
但**批次36 之前存的老记录缺这个字段，按 `full_access` 读**——否则恢复一个老会话会凭空每步弹审批）。
`status` 词汇表：`created | running | awaiting_human | stopping | finished | stopped | failed`，
前端 `isRunning` 只认前三个。

**`awaiting_human` 是驻留态，不是瞬时态**（2026-09-21 A 项起服务端这条可信）：图停在 interrupt 时
`_run`/`_resume` 的收尾不再把它覆写成 `finished`（旧行为下前端靠 SSE 事件本地补一刀
`stores/sessions.ts:414`，刷新一次 GET 就变「已完成」）。这个状态下只有两条去路，端点各自说清：
回答 = `POST /human-input`（200 起 resume；有活任务时 409，见 B2）；放弃 = `POST /stop`
（就地落 `stopped`，**不**转发 `ch:ctl`——此刻全集群没有活任务，转发只会把会话钉死在 `stopping`）。
`POST /start` 在这个状态回 409 且 detail 给出上述两条去路，重开一场绕不过断点。

`feedback` 的**票值两态**（B4 加时刻后新增的口径，读侧必须两边都吃）：`"like"` = 2026-09-23 之前投的旧票，**没有时刻**；`{"v": "like", "at": "YYYY-MM-DD HH:MM:SS"}` = 新票（`at` 与 `created_at` 同一个 `_now()` 格式）。归一规则只有一份，两端各一份同实现：后端 `server/api/sessions.py::_vote_of`、前端 `frontend/src/utils/votes.ts::parseVote`。⚠ 旧票**同票幂等**时会原地保留裸字符串（没变化就不写），这不是漏归一——读侧负责兼容。按时间分那一视图里旧票单独成「未记时刻」一档，**不拿 `created_at` 顶上**。`GET/PUT /{sid}/feedback` 的 `votes`/`feedback` 字段、以及 SSE `kind="feedback"` 的 `value`（`{key, vote, at}`）都按这份口径。

⚠ **归一只有一份，吃票的读侧却有好几处**（每个都得先过 `parseVote`／`_vote_of`，漏一处就出现「接口对了、读出来的数错了」）：① 会话投影 `stores/sessions.ts::loadFeedback`；② PUT/DELETE 回执 `MessageIconActions.vue`；**③ 活流 `kind="feedback"` 分支——它不在这份名单里，别去给它补一层归一**（事件 `value` 是**扁平** `{key, vote, at}`，`vote` 本来就是字符串、`clear` 时是空串，从不是两态存储值；在这里再套一次 `parseVote` 只会把「路径写对」变成「看起来写对」，那是真假绿）；④ 用量页聚合 `utils/stats.ts::countVotes`；⑤ 按票筛与按天分 `utils/votes.ts::{filterRowsByVote, voteBuckets}`。09-23 两次踩坑都在这种地方：② 让「再点一次取消」静默变成「又投一次」，④ 把三张带时刻的真票数成「未识别 4」——两次端点判据都是全绿，只有活体读数看得见。**09-23 04:2x 三条通路各取过一次活体读数**（真 Chrome + 一条真会话的真尾行 `t:stream-act`）：回执 `PUT→200` 时字形换成 `like-fill`、再点一次发 `DELETE`、改投时 `at` 前进；带外 PUT 经事件让图标跟上，且在该状态下再点「没用」发的是 `DELETE` 不是 PUT；切走再切回走投影通路、零写请求而图标仍亮。顺带一条**判据设计事实**：把 ② 那行的 `normalizeVotes` 摘掉，1.8s 采样粒度的活体探针**看不见**（组件写进 store 的裸对象在 ~150ms 内被它自己的事件回执盖回去），② 处归一真正承重的是**事件落地前那 150ms 与 SSE 断线（`stream==='down'`）那一档** ⇒ 钉它靠源级断言＋纯函数单测，活体读数的位置在「三通路互不打脸」。

`Span`（`/trace`）：`node · pt · ct · cost_usd · cost_cny · ts · t0 · ft`。

`CheckpointHead`（`/checkpoints`，C11）：`checkpoint_id · step · source · ts · next · writes · tasks`。
**刻意没有 `state`/`values`**——一个会话最多实测到 711 份超步、单份最大 62 KB，整份跟着列表回就是几十 MB；
黑板内容只在点某一行时从 `/checkpoints/{checkpoint_id}` 取一份（超上限 413，前端按 `status` 分流）。
翻页与 `/events/history` 同判：`before` 是**开区间**上界（传上一页末条 id），`has_more` 由服务端多取一条判。

`cost` 快照（GET 会话的 `cost` 字段与 SSE `status` 事件里那份，同一个出口 `runner.cost_snapshot`）：
`cost_usd · cost_cny · total_prompt_tokens · total_completion_tokens · truncated_calls · unknown_command_calls`。
后两个是**只读计数**（B8 截断 / T4-③ 模型吐未知命令被回喂），不是金额、也不与两桶相加；它们进这份快照的理由与 token 一样——这是唯一被持久化并由列表出口带出的 dict，用量页的跨会话求和只能吃它（`frontend/src/utils/stats.ts::wasteTotals`）。
**没有 `total_cost`**（C12 拍板：删掉、不留兼容字段）——根因是 `TOKEN_COSTS` 里人民币行与美元行
同表混存，两种币价加在一个无单位 float 上，报出来的数既不是美元也不是人民币。
现在记账端按 `CNY_MODELS` 分桶、**不换算汇率**，展示端各标各符号（`frontend/src/utils/money.ts`
是唯一出口）；老记录里残留的 `total_cost` 前后端都不读。`step-3.5-flash` 这类分「缓存命中/未命中」
两档的价，本表按**未命中**那档记（usage 里没有可用的 cache_read 信号），宁可高估。
**单位是 unix 秒（浮点），不是毫秒。** `t0`=LLM 派发时刻、`ft`=首 token 时刻，由
`server/runner.py` 按 `run_id` 攒（批次16 起）；**老会话的 span 里这两个字段是 `null`**，
前端据此不显示 TTFT/耗时，而不是显示一个 0。

`FileNode`：`name · path · type('dir'|'file') · size? · ext? · children?`。

## 4. SSE 事件信封

`Event` 11 字段：`session_id · seq · ts · cursor · kind · block · uuid · name · value · role · extra`。

| 词汇表 | 取值 |
|---|---|
| `kind`（10） | `report` `log` `status` `ask_human` `approval` `error` `turn` `goal` `queue` `feedback` |
| `block`（9，`codeharness/report.py:BlockType`） | `Thought` `Docs` `Editor` `Notebook` `Terminal` `Task` `Browser` `Browser-RT` `Gallery` |
| `name`（report 的分派键） | `meta` `content` `document` `object` `cmd` `output` `path` `url` `page` `end_marker` |

**`queue` 的 `name` 是 `add` / `remove` / `drain`**，`value={"items":[{id,content,send_to}]}`：
`add` 由 HTTP 线程投（FastAPI 的同步端点跑在线程池里，与 route 的取不同线程——正因如此留痕做在队列
而不是做在某一侧），`drain` 由跑图的一侧发（= 已投递，胶囊该消失），`remove` 是用户撤回。
前端只按 id 增删这一份投影，**绝不整份覆盖**（覆盖会把「刚 add、GET 还没回」的那条吞掉）。

**`goal` 的 `name` 就是参照系的 `operation`**（`create`/`edit`/`complete`/`clear`，取
`packages/goal/goal/src/domain.ts:14-21`），`value={"objective","done_at"}` 带当前全值。
它是**通知不是真值**：真值在 `Session.goal`/`goal_done_at`（GET 就拿得到），所以前端只拿它刷新本地那条
会话，不另起第二份状态；`clear` 的 objective 是空串，必须照收。参照系的 paused/blocked 两档本仓**没有生产者**，
所以不发也不渲染（摆了就是 C2 那种「看起来有其实没有」）。

前端 `stores/sessions.ts:applyEvent()` 的落点：`report` 按 `uuid` 聚成块、按 `name` 填字段；
`log` 进右栏日志；`status` 更新状态点与成本；`ask_human` 顶掉 composer；`approval` 按 `name` 进出队
（`requested` 入队并顶掉 composer 出审批卡，`resolved` 只出队——会话回到什么状态由紧随其后的
`status` 事件说，这里不猜）；`error` 进日志。
`User` 是**前端伪块**（`sendChat` 本地插的气泡），后端不发。
`System` 也不是 BlockType，它只是 `ChatNode` 对未匹配类型的兜底标题。

**`turn/end` 只有一种语义**：`value={"reason": {"kind": "max-tokens"}}`，即「这一跑里至少有一步
被输出 token 上限截断」（B8；形状取自参照系 `conversation-nodes/turn-max-tokens.ts:42`）。
发出点在 `server/runner.py::_settle` → `_publish_max_tokens`，**收口时一条、不重复**（`resume`
过的长跑用 `_trunc_reported` 记「上次报到第几笔」）。为什么不在 `_translate` 的
`on_chat_model_end` 上顺手发：那条钩子在「JSON 被切半→解析失败」这种最伤的截断上收不到信号，
而且这种调用连账都不落（见 `PLAN §4 C17`）；每笔**落了账**的调用都把自己的 `response_metadata`
带进 `CostManager.add_usage`，那是当前唯一不漏的口。前端把它建成 `type='MaxTokens'` 的块
（`'MaxTokens'` 同样不是 BlockType，t1 查不到，判据在 **t16**），渲染成 warn 档的一行提示。

**游标铁律**（这条改错过一次线上丢 9% 事件）：Redis 总线的 `seq = ms*10^6+cnt ≈ 1.79e18`
远超 `2^53`，过 `JSON.parse` 会舍入到 ulp=256，同毫秒内上千事件塌缩成几个值。所以
**去重与续传只认 `cursor`**（定宽补零字符串，字典序即等于到达序），`seq` 只能拿来展示。
`after` 参数收串、也吃裸数字做兼容。

## 5. 鉴权

开关是 **`PLATFORM__AUTH_ENABLED`**（`settings.py:97`，默认 `False`；`.env` 与 `docker-compose.yml`
都没设它 → 单机开发态恒关）。**注意别写 `PLATFORM__AUTH=1`**：`env_nested_delimiter="__"` 下段名必须等于
字段名，实测 `PLATFORM__AUTH=1` 打不开（`auth_enabled` 仍 `False`），只有 `PLATFORM__AUTH_ENABLED=1` 生效
（`auth.py:3` 的旧说法已按此更正）。
`PLATFORM__AUTH_ENABLED` 关时 `current_user` 恒返回 `"default"`（现状），开时全路由校验 Bearer 并
**按 user 隔离，越权一律 404 不泄露存在性**。
坑：`EventSource` 发不出 `Authorization` 头，所以 auth 开启时 token 走
`?access_token=` 查询参数（`client.ts` 的 Bearer 只管 `fetch`；实现 `server/auth.py:157`，
token 进 URL 有进日志的风险、仅 SSE 消费，换 cookie 是升级路径）。

### 5.1 已知边界：**登录态不跨 worker**（按边界处理，不再当 bug 追）

三样状态在**进程内**（`server/auth.py`），所以 `PLATFORM__AUTH_ENABLED=1` 且 `uvicorn --workers >1`
同时成立时各自为政：

| 进程内状态 | 落点 | 多 worker 下的后果 | 升级路径（文件里自述） |
|---|---|---|---|
| token 表 `_Tokens._t` | `auth.py:116-140`，模块级单例 `:141` | 登录落在 A 进程、下一请求被轮到 B 进程 → **401 登录已过期**，表现为「偶发掉线」 | token 存 redis（`chat_factory` 同款注入） |
| 登录失败计数 `_login_fails` | `auth.py:77-115` | 各进程各算各的：5 次/60s 实际变 5×N，限速形同放宽 | 计数进 redis |
| 用户表 `server/data/users.json` | `auth.py:35` 读、`:52` 写，串行靠 `threading.Lock`（`:32`） | 线程锁不互斥进程 → 两 worker 各自 load-modify-save，**后写的把先写的账号抹掉**（原子 rename 只防撕裂写，不防 lost update） | 换共享存储 |
| 重启即失效 | TTL 7 天但表在内存 | **重启要重登**（单机可接受，`auth.py:9` 自述） | 同上 |

**边界已实测（2026-09-21 10:58，两个独立进程 = 两个 worker 的真实形态；`TestClient` 不起端口、不碰共享 Redis）**：
A 进程注册拿到的票在 B 进程 `GET /api/auth/me` → **401「登录已过期」**，而**同一口令在 B 重新登录 → 200**、
B 自己签发的票 → 200 —— 这个不对称就是本条边界的形状（`users.json` 是共享文件、`_Tokens` 是进程内表）。
查询参数那条路（SSE 用的）与 Bearer 等价（同一张票 `?access_token=` → 200）；无票与错密码各 401；
进程内失败计数实测 `[401, 401, 401, 401, 401, 429, 429]` → 每 worker 各 5 次/60s，**N 个 worker 就是 5×N 次机会**。
读数落盘 `log/c10_probe_A.out`/`_B.out`/`_C.out`，脚本 `log/c10_probe_authproc.py`。

**同族的单机侧（F-D，2026-09-21 17:2x 实测补）**：`users.json` 在**单进程内**的并发也不是免费的。
Windows 上写者的 `tmp.replace()` 与读者的 `read_text()` 撞在一起回 `WinError 5/32`（旧写法实测
4 线程 × 8 轮 = **18 次报错**），而两笔写共用一支**固定名** scratch 会把表写成半新半旧的坏 JSON
（前缀短、尾巴长，`_load_users` 从此必炸）。现在：写侧一次性 scratch 名 + rename 有界重试，
读侧 170ms 内重试；判据 `tests/s20::t1b` 四格，④是对照组（旧写法本体，必须报错）。
**这不改变上面那条边界**——跨进程依旧会丢账号，升级路径仍是换共享存储。

**为什么今天打不到**：`docker-compose.yml:31` 把后端钉在 `--workers 1`，且 compose 的 environment 与本机
`.env` **都没开 auth** → 默认「auth 关 + 单 worker」，两个开关同时翻转才踩得到。多 worker 本身不是没验过：
`docs/施工4:65` 记了 `--workers 2` + redis 的真进程冒烟（/graph、/trace、/events/history 跨 worker 正常），
但那一轮没开 auth，**鉴权面不在它的覆盖里**。另注：`server/runner.py:132,348` 的 `graphs[sid]` 同样是进程内字典，
它的多 worker 处置记在 `施工4:21`（那里写的 `runner.py:25` 是旧行号，实测该处现在是 `CostManager()`，引用前重新 grep），与鉴权无关，别混。

**要提 `--workers` 之前**：必须先做完上表「升级路径」那一列（token + 失败计数进 redis、users 换共享存储），
否则等于把「随机 401」和「注册丢账号」放进出口。反过来说，只要部署形态还是 `--workers 1`，
这四条就**按已知边界对待，别再当 bug 排查**。
