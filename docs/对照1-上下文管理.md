# 对照 1 · 上下文管理 · 本项目 vs 源 MetaGPT

> **这套文档在回答什么**：源项目 `E:\MetaGPT\metagpt`（`setup.py:100` version=1.0.0）的这块能力，在本项目 `E:\Codeharness` 里到底实现了没有、实现到什么程度。本项目是**换栈重实现**（Python + FastAPI + LangChain/LangGraph + Vue3 + Pydantic + Qdrant + Redis），不是 fork，所以判据是「能力覆盖 + 机制现代化」，不是文件数。
>
> 状态词汇（六份文档统一）：`已复刻` = 语义等价落地；`现代化替换` = 换成了新栈的原生形态、能力不减；`部分实现` = 有实现但覆盖面或接线不足；`未实现` = 找不着对应物；`有意不做` = 判定账本 `docs/判定-复制与重构清单.md` 里明令不搬。
>
> 配套账本：判定与去向记在 `判定-复制与重构清单.md`，施工步骤记在 `施工1~4`。本文件只记**现状核对**。

## 结论速览

**实现度：约 65%。** 上下文管理是六个子系统里现代化替换最彻底的一片（角色私有记忆、条数窗口、摘要滚动、向量溢出、断点续跑、多租户切片全都换了底座，其中几处比源更强），但**兜底最薄**：源在 LLM 出口强制的 token 级压缩，本仓整件缺失，长会话没有防撞上下文墙的机制。

三条最要紧的缺口：

1. **`compress_messages` 整件未落地**——源的压缩发生在 `provider/base_llm.py:207`，是每次 `aask` 前的强制动作；本仓 `provider/gateway.py:130-163` 直接把 messages 交给 `ChatOpenAI`，中间没有任何钩子。配置项 `compress_type`（`configs/llm_config.py:105`）能设、能 import，**行为永不发生**。
2. **经典线 `Agent` 从不回喂历史**——`roles/agent.py:126` 的 prompt 只由当轮 `inbox` 拼成，`s["memory"]` 仅在 inbox 空时取最后一条（`:129`）。上游 PRD/设计全文不进 prompt，跨角色的上下文全靠 `instruct_content` 显式透传（`:146`）。
3. **`MessageQueue` 是有定义无运行时的复制件**——`schema.py:508-572` 完整（还补了 `load`），生产代码零实例化；图里跑的是 `AgentState.inbox`（`agent.py:17`）与 `Send({"_inbox": [...]})`（`team_graph.py:104,119`）。

## 四、缺口与风险（按优先级）

1. **无 token 兜底 = 长会话必炸（最高危）**。源在 provider 层唯一出口强制压缩，本仓 `gateway.ainvoke`（`:130-156`）直接发给模型。后果：会话拉长后表现为 HTTP 400 或 `LengthFinishReasonError`，而后者在 `gateway.py:253` 被当作「输出被截断」处理，**不是**输入超窗，报出来的错会误导排查方向。收口点只有一处：`ainvoke` 进门时按 `context_length` 裁剪，一处覆盖两条线。
2. **经典线记忆不回喂**。`agent.py:126` 之后，第二、三个动作看不到第一个动作的产物全文，只能看到 `instruct_content` 透传的结构体（`:146`）。源里对应机制是 `rc.memory` 全量入 prompt。当前之所以没暴露，是因为经典线五角色链每角色基本只跑一两个动作，且 SOP 产物都走 `CONTEXT_WIRING` 显式装配——一旦有角色在同一轮里做多轮修订，这个洞就会现形。
3. **REACT 选择只看一条消息的 2000 字**。`agent.py:107` 硬编码 `s["inbox"][-1].content[:2000]`，无 token 口径。源的 REACT 是把整个 memory 交给模型选数字。
4. **`Agent` 侧零压缩**。`_compress` 只存在于 `role_zero.py:110`；`s["memory"]` 在 `TeamState.memories` 里**只增不减**，长会话的存储与（一旦接线后的）prompt 都会线性膨胀。
5. **压缩配置是残缺复制**。`configs/compress_msg_config.py:7-21` 缺源 `__missing__`（未知值退化为 NO_COMPRESS）与 `get_type`/`cut_types`；从环境变量传一个不认识的压缩类型会直接 pydantic 校验失败，而源是静默退化。

## 五、「看着像有、其实没接线」

按危害排序。这一节是本套文档的重点：判定账本已经说明**该不该搬**，这一节说明**搬了的那部分是不是真的在跑**。

1. `schema.py:508` `MessageQueue` + `:563 load` 生产零实例化（唯一 `MessageQueue()` 出现在测试和它自己的 `load` 里）。文件头注释还在讲「曾把队列写成类属性导致两个会话消息互串」的修复史——**修的是一个没人跑的类**。要么接进 `_observe`，要么删。
2. `configs/compress_msg_config.py:7 CompressType` → `llm_config.py:105 compress_type` → **全仓无读取方**。源消费点在 `base_llm.py:207`，本仓 `aask`（`:158-163`）直落 `ainvoke`，中间无钩子。唯一的"命中"是 `tests/s2_gateway.py:276` 断 LLMConfig 的**字段名列表**含 `compress_type`——纯配置面检查，不测行为。
3. `gateway.py:120 count_tokens` 除自身 docstring 外零调用方（`utils/text.py:3` 只用 `count_output_tokens`，且仅 `actions/research.py:106` 一处）。而 `gateway.py:14` 的文档头声称「三件事在这里收口：token 计数」——实际收口的是 API 返回的 usage，不是这个函数。
4. `team_graph.py:21 memories` 有写方（`agent.py:183`）无读方：`as_node:180` 只在**同一角色被再次激活**时读回，经典线一轮里每个角色通常只激活一次，等于「持久化了但没用」。
5. `agent.py:19 action_cursor` 注释自称等价源的 `RoleContext.state`，但源 `role.py:348-356` 的语义是**从断点动作续跑**；本仓 `as_node:182` 每次激活把游标重置为 -1。中断恢复目前只有图级（LangGraph resume），角色内游标不续。
6. `memory/brain_memory.py:77 is_overflow`（阈值 `memory_overflow_size=200`）零调用方——真正触发压缩的是 `role_zero.py:112` 自己比 `len(storage) > memory_k`。（注：`s5_memory_rag.py` 的 `t4` 断言的是「溢出判定有读者」，读它的是测试不是生产。）
7. `const.py:168 DEFAULT_MAX_TOKEN_COUNT` 零读者；`llm_config.py:99 context_length` 零读者——**本可以用它做兜底的地方，正是没人接的地方**。

## 六、门禁覆盖

真覆盖（`tests/` 是自测脚本，不吃 pytest）：

- `s5_memory_rag.py:190-203` t8 截窗只在组 prompt 时生效；`:205-225` t9 溢出→摘要→Redis→恢复；`:227-236` t10 key 按会话+角色隔离；`:183-195` t7 工具结果确实出现在下一轮 messages；`:405-435` 长期记忆不可用时的降级。
- `s3b_runtime.py:267` t11 `watch` × SOP 双向自洽（含 `Agent._observe` 行为级断言）。
- `s1_schema.py:202,210` 只测 `MessageQueue` 队列语义本身，不测它是否被图使用。

零断言：`compress_messages` 的任何等价物；`LLMGateway.count_tokens`；`MessageQueue` 的运行时接线；`Agent` 记忆随轮次增长后的 prompt 体积；`DEFAULT_MAX_TOKEN_COUNT` / `context_length` 生效路径。**换句话说：上下文这一片「怎么攒起来」有门禁，「太长怎么办」一条断言都没有。**

## 七、建议的收口顺序

1. 在 `gateway.ainvoke` 进门处补 token 兜底（源的 pre/post × by_msg/by_token 四策略，或直接 LangChain `trim_messages`），同时让 `compress_type` / `context_length` 成为它的输入——一次动作把 §四-1、§五-2、§五-3、§五-7 全部收敛。
2. 加一条不花钱的门禁：FakeLLM + 超长输入，断言出口 messages 的 token 数不超 `context_length × threshold`。这条门禁是第 1 步存在性的证据。
3. 决定 `MessageQueue` 的去留（接进 `_observe` 或删掉并在判定表登记），别让注释继续讲一个不存在的问题的修复史。
4. 经典线记忆回喂按「条数窗口 + 摘要」做（照 `role_zero.py:110-147` 现成的那套），不要新写第三种。
