## 结论速览

**实现度：约 70%。角色清单 18/18 全有注册件（无一缺失，`s6 t17` 逐字对账钉住），外部注册新角色这条源没做成的扩展点本项目真做成了；打折的是「角色的个性」与「动态线的委派」，本轮 B1 又新增了一批「复制进来但没装配」的死资产。**

四条最要紧的缺口：

1. **具名角色在动态模式下近乎同质**（本子系统最大的实现度折扣，本轮未动）：`RoleZero.__init__` 有 `instruction` 形参（`roles/role_zero.py:47`，默认 `ROLE_INSTRUCTION`），但 `roles/registry.py` 的 18 个工厂里**只有两个传了 instruction**（`:76` Assistant、`:89` SweAgent，且都是新写的英文字面量，不是源资产）。ProductManager/Architect/Engineer2/TeamLeader/DataAnalyst 等落到默认 `ROLE_INSTRUCTION`，于是这些角色之间只有 `name`/`goal` 有别。后果连带：`prompts/di/{architect,engineer2,data_analyst,team_leader}.py` 与 `prompts/product_manager.py` 里的角色专属 instruction 常量**全是死资产**——它们只被 `tests/s6_sop.py:67-70` 的 import 冒烟覆盖（除互相 import 外生产零读者）。
2. **动态线的多角色委派未实现**：源 `TeamLeader.publish_team_message`（`roles/di/team_leader.py:75-86`）+ `MGXEnv`（`environment/mgx/mgx_env.py:24-58`）能点名唤醒任意队友；本仓 `team.dynamic_assembly:65-71` 的注释自认：「本仓动态形态=单 RoleZero 工具循环（`Command.assignee` 只是展示字段，无委派路由），需求只喂队长、Alice/Bob 空转」。`default_team:7-10` 的角色名根本不在任何路由表内。本轮未动。
3. **14 个角色只验「能 build」，未验行为**：`tests/test_roles_registry.py` 对 Sales/CustomerService/Researcher/DataAnalyst/TutorialAssistant/InvoiceOCR 六族有真跑断言，其余只有实例化 + 可编译 + 有 `as_node`。本轮 B1 的新 action 也没带来任何角色级断言。
4. **无 per-role LLM 绑定**：源 `RoleCustomConfig` 本来就是死配置（§一 末），本项目走的是会话级 `llm_override` + `user_id`，即「一个会话一个模型」，不是「一个角色一个模型」。要做「队长用贵模型、工程师用便宜模型」需要新写。

## 四、「看着像有、其实没接线」

- **A. 死资产清单：角色专属 prompt**。`prompts/di/architect.py`、`di/engineer2.py`、`di/data_analyst.py`、`di/team_leader.py`、`di/swe_agent.py`、`di/write_analysis_code.py`、`product_manager.py`、`sales.py`、`tutorial_assistant.py`、`invoice_ocr.py` 里的 `*_INSTRUCTION` 常量，生产路径唯一读者是 `tests/s6_sop.py:67-70` 的 import 冒烟。**搬来了角色灵魂的那半截，装配时没接上。**
- **B. `default_team` 的三角色不参与默认兜底**：`team.py:8-10` 注释自己写着「这套角色名不在 `team_graph.SOP` 里……所以现在**不参与默认兜底**」，`_default_agents:88-95` 用的是 `classic_team`。而注释还留了一句血的教训：角色名对不上时 LangGraph 只打一行 "Ignoring unknown node name PM"，**整场会话零次 LLM 调用**（实测）。这条正是 §结论-2 委派未实现的技术成因——路由表里没有那些节点。
- **C. `Command.assignee` 是展示字段**：`role_zero.py:165` 一带产出，无路由读者（详见对照 6）。
- **D. `registry.py` 的闲置 import** 由 `s6_sop.py t17` 反向检查（该组会查 registry 里没用上的 import），所以这一类已经清了；但 profile 字段与 prompt 常量的对应关系不在它的断言范围内。
- **E.【本轮新增】B1 的 12 个 requirement_analysis action 是「复制进来但无人装配」**：`actions/requirement_analysis/{framework,trd,requirement}/*` 已落仓（`33a98f2`），但 ① `sop/templates.py:46-53` 的内置模板**只有 `classic_sop`**，没登记需求分析 SOP；② `grep requirement_analysis registry.py team.py sop/templates.py` 为空——**没有角色/工厂/模板引用这 12 件**。B1 计划里的「追加 `requirement_analysis_sop` 到 templates + `CreateSessionReq.paradigm="requirement"`」这一步**未落地**。于是这批 prompt/action 资产与 §五-A 的死 prompt 同族：搬来了、没通电。门禁 `s11/s6` 都没断它进会话。

## 五、门禁覆盖

- `tests/test_roles_registry.py`：① 18 角色全实例化 + 可编译 + 有 `as_node`（`:19-22`）；②③ Sales/CustomerService 的 `desc` 进 prefix；④⑤⑥⑦ Researcher / DataAnalyst / TutorialAssistant / InvoiceOCR **带剧本实跑**。→ **其余 14 个角色只验「能 build」**。
- `tests/s6_sop.py:611-683 t17`：AST 扫源 `roles/*.py` 抽 name/profile/goal，逐字比对 registry（≥30 字段），并查 registry 闲置 import。**profile 面钉得最死的一组，但它不断言装配后的行为。**
- `tests/s6_sop.py:686 t18`：`strategy` 换装 sop/react/role_zero 三态断言（本轮 `tot` 第四值由 `s14_tot t2/t3` 覆盖，但见对照 4 §五-新1：浅）。
- `tests/s6_sop.py:716-809 t19`：**不改内核**经 `ext_api` 注册 Action + Tool + Role(Poet) + SOP 模板 → `build_team(...).ainvoke` 跑完整场 + 四守卫 + 完全回滚。**「外部注册新角色能跑通会话」这条被 FakeLLM 门禁真断言**——这条比源强。
- `tests/manual_ext_ui.py`：同链路走真 server + 真模型 + UI 可见（Poet 的 Docs 块、`/graph`），但文件自述「真钱通道，不进门禁」（`:1-2`）。
- **零断言**：TeamLeader / ProductManager / Architect / Engineer2 / Assistant / SweAgent 的 RoleZero 族**委派与思考行为**；per-role instruction 是否进了 system_prompt；**B1 的 requirement_analysis 是否真进某张 SOP 模板**（§四-E，因为根本没进）。

## 六、建议的收口顺序

1. **把角色 instruction 接上**（最小改动、最高收益，本轮未动）：`registry.py` 各 RoleZero 族工厂补 `instruction=<对应常量>`，一行一个工厂。做完 §结论-1 与 §五-A 同时消失，且 `t17` 那套 AST 对账可以顺势扩成「profile 引用的 prompt 常量必须真被工厂使用」。
2. **B1 的 SOP 要么登记要么删**（本轮新账）：若要需求分析这条垂直线真能用，按 B1 原计划在 `sop/templates.py` 用 `register_template` 登记 `requirement_analysis_sop`（assemble + edges）并给 `CreateSessionReq.paradigm/sop` 加值，让 12 件进装配 + 一条 FakeLLM 门禁断言「选该模板能跑完整场」；若暂不做，就把 12 件挪出主包或标注为「待接线的资产」，别让 `requirement_analysis/` 顶着一个「已落地 SOP」的名。
3. **委派要么做、要么明确判弃**：真做就是在 `dynamic_assembly` 的路由表里加上队友节点 + 让 `Command.assignee` 成为 `Send` 目标（机制在对照 6 §三 已列）；不做就在 `判定-复制与重构清单.md` 里补一条「多角色动态委派 = 有意不做，本仓动态线是单引擎」，别让 `default_team` 顶着三个空转角色名。
4. 给其余 14 个角色各补一条最便宜的剧本断言（照 ④⑤⑥⑦ 的姿势，FakeLLM 零成本），优先 TeamLeader/Architect/Engineer2——它们是 `t17` 之外唯一能证明「角色不只是字典」的东西。
5. per-role 模型绑定：等平台真要跑「队长贵模型 + 工程师便宜模型」的账再做，现在缺的是 `build_role` 接受 llm override，不是设计问题。
